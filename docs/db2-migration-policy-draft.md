## 2. テーブル定義・データ型・DDL移行方針

### 2.1 データ型マッピング方針（案）
現行PostgreSQLのDDL／定義書を確認し、Db2の標準型へマッピングする。

| PostgreSQL 型 | Db2 移行先型（案） | 変換・確認ポイント |
| :--- | :--- | :--- |
| `SERIAL` / `BIGSERIAL` | `INTEGER` / `BIGINT` + `GENERATED ALWAYS AS IDENTITY`（または `SEQUENCE`） | 採番ルール・初期値・増分値を確認 |
| `VARCHAR(n)` | `VARCHAR(n)` | 文字数ではなく**バイト数**で扱われるケースやUTF-8時の最大長に注意 |
| `TEXT` | `VARCHAR(最大長)` または `CLOB` | 想定最大文字数を見積もり、インデックス対象カラムか確認 |
| `INTEGER` / `BIGINT` | `INTEGER` / `BIGINT` | 桁あふれ・Java側エンティティ型との整合を確認 |
| `NUMERIC(p,s)` / `DECIMAL` | `DECIMAL(p,s)` | 金額・数量などの丸め・精度仕様を確認 |
| `BOOLEAN` | `BOOLEAN` または `SMALLINT`（`1`/`0`） | Db2バージョンおよびJDBCドライバ・Java側の扱いを確認 |
| `TIMESTAMP` / `TIMESTAMPTZ` | `TIMESTAMP` | タイムゾーン扱いの統一ルールを確認 |

### 2.2 制約・インデックス・DDL作成ルール（案）
- **主キー・外部キー・一意制約**：テーブル作成時またはDDLスクリプト内で定義し、投入順序（親テーブル→子テーブル）を整理する。
- **DEFAULT値・NOT NULL**：現行定義のデフォルト値（定数・現在日時など）がDb2でも同等に評価されるか確認する。

## 4. データ移行・SQL検証方針

### 4.1 データ移行（案）
- 移行対象テーブル一覧（全 `[要確認・追記：N]` テーブル）ごとに移行手順・順序を確定する。
- 文字コード（UTF-8等）、改行コード、NULL／空文字、日付フォーマットによる取り込みエラーがないか確認する。
- ID採番カラムへ明示的に値を投入する場合は、移行後にIDの採番位置（`RESTART WITH` 等）を最新値へ合わせる。

### 4.2 SQL検証（案）
- **データ整合性確認**：移行元・移行先でのテーブル別レコード件数一致、主要カラムの集計値・サンプルデータ照合。
- **SQL／アプリ連携確認**：機能チームが抽出・修正したSQLおよびJava側処理と連携し、検索・登録・更新・削除が期待通りに動作することを確認する。
