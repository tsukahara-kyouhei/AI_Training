## 1. 背景と目的

商品検索のヒット率低下が離脱率増加の主要因と考えられる。  
現状の検索機能はキーワードマッチングの精度が低く、検索結果の絞り込み項目が不足している。  
本改善により検索ヒット率を向上させ、顧客の離脱率低下を図る。

## 4. 機能要件（TO-BE）

### 4.1 キーワード検索対象フィールドの拡張

キーワード検索の対象フィールドを以下のとおり変更・追加する。

| フィールド | テーブル・カラム | マッチング方式 | 変更区分 |
|---|---|---|---|
| 商品名 | `products.product_name` | 部分一致 | 変更なし |
| バリエーション名 | `products.variation_name` | 部分一致 | **新規追加** |
| 商品紹介文 | `products.description` | 部分一致 | **新規追加** |
| 商品コード | `product_variants.product_code` | **完全一致と前方一致の両方**を同時に OR 検索 | **変更** |

#### 商品コードのマッチング変更理由

商品コードに中間一致を用いると、コードの一部の数字が別の商品コードに偶然含まれ、意図しない商品がヒットするケースが発生する。  
**完全一致と前方一致の両方を同時にOR検索する**仕様に変更する。  
例：`DSK-001` と入力した場合、`product_code = 'DSK-001'`（完全一致）と `product_code LIKE 'DSK-001%'`（前方一致）の両条件をORで適用する。

#### 複数フィールドの検索ロジック

各フィールドへの条件は OR で結合する。いずれか 1 フィールドでもマッチした商品を結果に含める。

```
（商品名 部分一致）
OR （バリエーション名 部分一致）
OR （商品紹介文 部分一致）
OR （商品コード 完全一致 OR 商品コード 前方一致）
```

### 4.2 文字の正規化

検索の使い勝手を向上させるため、以下の正規化を適用する。  
正規化はキーワード入力値とDB格納値の**双方**に同一ルールで適用し、比較時の表記揺れをなくす。

#### 4.2.1 英字の大文字小文字

大文字・小文字を区別せず検索する。

- 入力 `desk` → `DESK`・`Desk`・`desk` のいずれにもマッチ

> PostgreSQL の `ILIKE` 演算子を使用するため、現状でも部分的に対応済みだが、  
> 以下の全角半角正規化と組み合わせて統一仕様として扱う。

#### 4.2.2 数字・英字・カタカナの全角半角

数字・英字・カタカナについて、全角・半角を区別せず検索する。  
入力キーワードの**全角版と半角版の両パターンを生成し、いずれかにマッチすればヒット**とする（OR検索）。DBデータは変更しない。

| 変換対象 | 入力が全角の場合の検索パターン | 入力が半角の場合の検索パターン |
|---|---|---|
| 数字 | `１２３` → `１２３` と `123` でOR検索 | `123` → `123` と `１２３` でOR検索 |
| 英字 | `ＡＢＣ` → `ＡＢＣ` と `ABC` でOR検索 | `ABC` → `ABC` と `ＡＢＣ` でOR検索 |
| カタカナ | `デスク` → `デスク` と `ﾃﾞｽｸ` でOR検索 | `ﾃﾞｽｸ` → `ﾃﾞｽｸ` と `デスク` でOR検索 |

> **実装方針（決定事項）**  
> アプリケーション層（Java）で入力キーワードから「全角版」「半角版」の両パターンを生成し、  
> SQL の検索条件として OR で結合する。DBデータの変更・マイグレーションは不要。  
> 例：キーワード `ﾃﾞｽｸ` が入力された場合、`ﾃﾞｽｸ` と `デスク` の双方で部分一致検索を行う。

### 4.3 検索結果画面へのテイスト絞り込み追加

検索結果一覧画面の絞り込みパネルに「テイスト」条件を追加する。

#### 4.3.1 表示仕様

テイストはカテゴリごとに独立したマスタを持つため、検索結果画面ではカテゴリ別グループに分けて表示する。

| グループ | 選択肢の取得元 | フィルタ対象カラム |
|---|---|---|
| デスク | `desk_tastes`（`is_active = true` のもの） | `product_desk_attributes.taste_id` |
| チェア | `chair_tastes`（`is_active = true` のもの） | `product_chair_attributes.taste_id` |
| 収納家具 | `storage_tastes`（`is_active = true` のもの） | `product_storage_attributes.taste_id` |

- 各グループ内の選択肢はチェックボックスでの複数選択を可能とする。
- 候補が 0 件のグループは表示しない。
- 選択肢の並びはマスタの `sort_order` 順に従う。
- UIの見た目はカテゴリ一覧ページのテイスト絞り込みと同一にする。

#### 4.3.2 フィルタロジック

テイストフィルタは**カテゴリ別に独立して適用**する。あるカテゴリのテイストを選択しても、他カテゴリの商品はそのテイストで絞り込まれない。

| ケース | 動作 |
|---|---|
| テイスト未選択 | テイストによるフィルタなし（全カテゴリの商品が対象） |
| 同一グループ内を複数選択 | OR 条件（例：デスクのテイストAまたはB） |
| 異なるグループを選択（例：デスクとチェアのテイストを同時選択） | カテゴリ別に独立してフィルタを適用。デスク商品は選択したデスクテイストで絞り込み、チェア商品は選択したチェアテイストで絞り込む。テイストを選択していないカテゴリの商品はフィルタなし（引き続き表示）。 |

**例：デスクテイスト「ナチュラル」のみ選択した場合**
- デスク商品 → ナチュラルに一致するものだけ表示
- チェア商品 → テイスト条件なし（すべて表示）
- 収納家具商品 → テイスト条件なし（すべて表示）

#### 4.3.3 URLパラメータ

既存パラメータ体系を拡張し、テイスト条件を以下のパラメータで受け付ける。

| パラメータ名 | 型 | 多重指定 | 説明 |
|---|---|---|---|
| `deskTaste` | integer | 可 | デスクテイストID |
| `chairTaste` | integer | 可 | チェアテイストID |
| `storageTaste` | integer | 可 | 収納テイストID |

例: `/products/search?q=デスク&deskTaste=1&deskTaste=3&chairTaste=2`

#### 4.3.4 リセット動作

絞り込みリセット時はテイスト条件も含めてリセットする（既存リセット動作に準拠）。

### 4.4 変更しない項目

以下の機能は現状仕様を踏襲し、変更しない。

- 在庫有りのみ表示フィルタ
- 価格帯フィルタ（6段階）
- カラーフィルタ
- 並び順（おすすめ順・新しい順・価格の安い順・価格の高い順）
- 表示件数選択（15件・30件・60件）
- ページネーション仕様
- 商品カードの表示内容
- セッション・認証に関する動作（未ログイン・ログイン済みともに利用可能）

## 5. 非機能要件

### 5.1 性能要件

| 項目 | 目標値 | 計測条件 |
|---|---|---|
| 検索対象商品数（最大想定） | 1,000件 | 販売中商品の最大件数 |
| 初回表示応答時間（95パーセンタイル） | 2秒以内 | サーバー受信からHTMLレスポンス送信完了まで。ネットワーク往復時間は含まない。 |
| 絞り込み変更時の応答時間（95パーセンタイル） | 2秒以内 | 同上 |

### 5.2 セキュリティ要件

- 検索キーワードはサーバー側で入力値検証・エスケープを行い、SQLインジェクションを防止する。
- テイストIDなどの数値パラメータはホワイトリスト（マスタ存在確認）による正規化を行い、不正値を無視する（既存の絞り込み条件と同等の扱い）。
- 検索キーワードはHTML描画時にエスケープし、XSSを防止する（Thymeleafの標準エスケープを利用）。
- 検索キーワードのログ出力はマスキングまたは長さ制限を行い、機密情報の混入を防ぐ。

### 5.3 運用要件

- テイストマスタの追加・変更は既存の各カテゴリテーブル（`desk_tastes` 等）で管理し、アプリデプロイ不要で反映されること。

## 7. データ要件

### 7.1 文字正規化の実装方式（決定）

文字正規化はDBデータを変更せず、アプリケーション層（Java）のクエリ時に実施する（**選択肢C に決定**）。DBスキーマ変更・データマイグレーションは不要。

| 選択肢 | 概要 | 採用可否 |
|---|---|---|
| ~~A. 検索用カラム追加~~ | ~~`products` 等に正規化済み文字列カラムを追加~~ | ~~非採用（DBデータ変更なし方針のため）~~ |
| ~~B. 既存カラム正規化~~ | ~~既存カラムを正規化形式で格納するよう仕様変更~~ | ~~非採用（DBデータ変更なし方針のため）~~ |
| **C. クエリ時正規化（採用）** | アプリ側でキーワードから全角・半角の両パターンを生成し、既存カラムと OR 条件で照合（DB変更なし） | **採用** |

### 7.2 新規クエリ

以下の新規データアクセスが発生する。

| 用途 | 概要 |
|---|---|
| 全カテゴリのテイスト候補取得 | `desk_tastes`・`chair_tastes`・`storage_tastes` の有効レコードを一括取得する |
| テイストIDによる商品フィルタ | 各カテゴリの属性テーブルの `taste_id` を使って商品を絞り込む（既存の `DeskAttributeFilter` 等の拡張） |
| バリエーション名・商品紹介文の文字列検索 | 既存の `BaseProductWhere` SQL フラグメントにフィールドを追加する |

## 9. スコープ外・将来課題

| 項目 | 理由・補足 |
|---|---|
| 検索結果のモバイルモーダル対応（テイスト追加） | 現状「簡易版」表示中のため、別途UIの完全実装後に対応する |
| 形態素解析・全文検索エンジン連携（Elasticsearch 等） | 本改修スコープを超えるため、ヒット率が依然低い場合の次段階施策として検討する |
| 検索ログの分析基盤 | 別途要件定義が必要 |
| 同義語・表記揺れ辞書対応（例：「チェア」と「椅子」） | 本改修スコープ外 |

## 10. 用語定義

| 用語 | 定義 |
|---|---|
| 商品コード | `product_variants.product_code`。バリアント（色違い）単位で付与される一意コード |
| バリエーション名 | `products.variation_name`。同一商品グループ内での区別名（例：「幅サイズ」） |
| テイスト | 商品デザインの傾向を示すカテゴリ属性（例：ナチュラル・モダン）。カテゴリ別マスタで管理 |
| 前方一致 | 先頭文字列が一致するマッチング（例：`ABC` → `ABC001`・`ABCdesk` はマッチ。`001ABC` はマッチしない） |
| 部分一致 | 文字列のどの位置にでも一致するマッチング（中間一致と同義） |
| 全角半角正規化 | 全角数字・英字・カタカナを半角に統一する（またはその逆方向に統一する）変換 |
