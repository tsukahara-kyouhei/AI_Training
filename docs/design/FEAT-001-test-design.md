# FEAT-001 テスト設計

## 1. 目的

各要件が実際に満たされていることを検証するテスト設計を定義する。

## 2. テスト観点

- 正常系
- 0件
- 完全一致
- 前方一致
- 部分一致
- 大文字/小文字
- 全角/半角
- 複数キーワード
- 複数フィルタ
- テイスト検索
- ページング
- ソート
- 不正パラメータ
- 境界値
- NULL
- 空文字
- セキュリティ
- 性能

## 3. テストケース一覧

### 3.1 正常系

1. `q=デスク` で検索し、商品一覧が表示される
2. `q=ABCDE` で商品コード検索を実行する
3. `q=office` で商品名または説明文が一致する
4. `priceBand=2&color=white` を併用する
5. `inStockOnly=true` を付けて検索する

### 3.2 0件

1. ヒットしないキーワードで 0 件になる
2. 存在しない `deskTaste` を指定した場合、0 件または empty result になる
3. 価格帯とカラーが不一致な組み合わせで 0 件になる

### 3.3 完全一致 / 前方一致

1. `P0001-C01` と完全一致する商品がヒットする
2. `P0001` は exact では `P0001` 自体と一致しないため、`LOWER(product_code) = :keywordExactNormalized` でヒットしない
3. `P0001` は prefix として `P0001-C01` / `P0001-C02` をヒットさせる
4. `P0001` は `P00010-C01` を prefix としてヒットさせない
5. `P0001` は `P0001XYZ` を prefix としてヒットさせない
6. `P0001` は `X0001-C01` を prefix としてヒットさせない
7. `P0001-C01` は prefix としても `P0001-C01` 自体はヒットするが、`P0001` とは exact では別扱いである
8. `0001` と `C01` は中間一致・後方一致の検索条件として対象外であり、ヒットしない

### 3.3.1 product_code 境界値テスト

1. 入力 `P0001` / DB `P0001-C01` -> prefix でヒットする
2. 入力 `P0001` / DB `P0001-C02` -> prefix でヒットする
3. 入力 `P0001` / DB `P00010-C01` -> prefix でヒットしない
4. 入力 `P0001` / DB `X0001-C01` -> prefix でヒットしない
5. 入力 `P0001` / DB `P0001` -> exact でヒットする
6. 入力 `P0001` / DB `P0001XYZ` -> prefix でヒットしない
7. 入力 `P0001` / DB `P0001-C01` と `P0001-C02` を併せて検索し、両方が prefix 条件に含まれることを確認する

### 3.4 部分一致

1. 商品名に `木製` が含まれる場合ヒット
2. 説明文に `耐久性` が含まれる場合ヒット
3. バリエーション名 `Office Basic Chair` に `office` が含まれる場合ヒット

### 3.5 大文字/小文字

1. `office` / `OFFICE` / `OfFiCe` を同一視して検索できる
2. `Desk` / `DESK` / `desk` が同一視される
3. `p0001-c01` / `P0001-C01` / `P0001-c01` が product_code exact/prefix で同一視される
4. `P0001` と `p0001` は同じ base code として prefix 判定される

### 3.6 全角/半角

1. `ｐ０００１－ｃ０１` は Java の `NFKC` で `p0001-c01` に正規化され、DB の `P0001-C01` と比較可能になる
2. `Ｏｆｆｉｃｅ` が `office` と同一視される
3. `ｶﾀｶﾅ` と `カタカナ` が同一視される
4. 全角ハイフンや全角数字の入力値は Java の `NFKC` により ASCII に正規化されることを確認する
5. 実データ上の `product_code` は ASCII 形式で保存されているため、DB 値自体に全角文字は存在しないことを確認する

### 3.6.1 特殊文字テスト

1. `P%001` を検索して `%` がワイルドカードとして解釈されず、`P%001` 自体の文字列としてリテラル評価されることを確認する
2. `P_001` を検索して `_` がワイルドカードとして解釈されず、`P_001` 自体の文字列としてリテラル評価されることを確認する
3. `P\001` を検索して バックスラッシュが `ESCAPE '\'` によりリテラル扱いになることを確認する
4. `P0001%` は `P0001` の prefix として扱わず、`%` をエスケープした上で、`P0001%` を文字列として検索する場合のみヒットする
5. `P0001` は `P0001-%` の prefix 条件によりヒットし、`P00010-C01` はヒットしない

### 3.6.2 exact / prefix / contains の生成例

- 入力 `P0001` → 正規化 `p0001` → exact `p0001` → prefix `p0001-%` → contains `%p0001%`
- 入力 `p0001-c01` → 正規化 `p0001-c01` → exact `p0001-c01` → prefix `p0001-c01%` → contains `%p0001-c01%`
- 入力 `ｐ０００１－ｃ０１` → NFKC 後 `p0001-c01` → exact `p0001-c01` → prefix `p0001-c01%` → contains `%p0001-c01%`
- 入力 `office%` → `office\%` へエスケープして contains で比較する

### 3.7 複数条件

1. キーワード + 価格帯 + 色 + 在庫ありを同時に指定する
2. 価格帯 OR 条件で複数選択時の動作を確認する
3. 色条件を複数選択した場合に OR として動作する

### 3.8 テイスト検索

1. `deskTaste=1&deskTaste=2` のような複数選択が OR として発火する
2. `chairTaste` と `color` が同時に指定されたときに AND になる
3. `storageTaste` の候補値が参照候補以外なら除外される

### 3.9 ページング

1. `page=1` で先頭ページが開く
2. `page=999` で最終ページへ補正される
3. `size=15`, `30`, `60` で件数が変化する

### 3.10 ソート

1. `sort=price_asc` で安い順
2. `sort=price_desc` で高い順
3. `sort=newest` で新着順
4. `sort=invalid` が default に置換される

### 3.11 不正パラメータ

1. `page=0` は page 1 に補正される
2. `size=99` は default 15 の扱いをする
3. `sort=` blank は default になる
4. `color=invalid` は無視される

### 3.12 境界値

1. 空文字キーワード
2. 前後空白付きキーワード
3. 1ページ目最初の商品
4. 最終ページ最終商品

### 3.13 NULL / 空文字

1. `q` missing -> keyword 無視
2. `q=` blank -> keyword 無視
3. `q=null` -> keyword 無視
4. `priceBand` missing -> no price filter

### 3.14 セキュリティ

1. `%`, `_` を含む検索文字列が SQL を壊さない
2. XSS として意図した HTML が画面に出ない
3. 不正な ID の入力が候補一覧外なら無視される

### 3.15 性能

1. 1000 件程度の検索で 2 秒以内の目標を確認する
2. 0件検索の応答時間を確認する
3. テイスト絞込付き検索で遅延が急増しないことを確認する

## 4. テスト実装方針

- Controller テスト: RequestParam を正しく受け取れること
- Service テスト: `ProductSearchCondition` の正規化が正しいこと
- Repository/SQL テスト: 条件が妥当な SQL パラメータになること
- Integration テスト: 画面レンダリング時に 0 件/検索結果が表示されること

## 5. 最終確認観点

- 実データと PostgreSQL の `ILIKE` の挙動に合わせて、大文字・小文字と全角・半角の比較が想定どおりかを確認する
- 画面のモバイル簡易フィルタの POST/GET 仕様は既存の GET 検索形式に合わせて実装する
- 実データでは `product_code` は `P0001-C01` 形式であり、全角の product_code は対象外であることを確認する
