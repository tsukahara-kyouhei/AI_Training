# FEAT-002 クーポン機能 UIフロー設計（最終版）

## 1. カート
1. ユーザーがクーポンコードを入力。
2. `POST /api/cart/coupon` を呼び出す。
3. サーバーでクーポンを検証・再計算し、成功時はクーポンコードをセッションに保存する。
4. 成功時は割引額・クーポン名・合計を更新し、解除ボタンを表示する。
5. 別クーポンが適用済みなら `COUPON_ALREADY_APPLIED`。上書きはしない。
6. `DELETE /api/cart/coupon` で解除し、セッションからクーポンコードを削除する。
7. 商品追加・削除・数量変更・一括削除はクーポンコードをセッションに保持する。クーポン割引額は確定扱いせず、注文確認時に再検証する。

### セッション状態

| 操作 | クーポン状態 |
|---|---|
| クーポン適用 | 検証成功時にコードと適用時の会員ID（ゲストはNULL）を保存 |
| クーポン解除 | セッションからコードを削除 |
| 商品追加・削除・数量変更・一括削除 | 保持 |
| 注文確認GET | 現在のカートで再検証。不成立なら解除 |
| 注文確定POST | DBトランザクション内で最終再検証 |
| 注文成功 | チェックアウト完了に伴いクーポン状態を削除 |
| 注文確定の再検証失敗 | クーポンを解除し、確定処理を行わない |
| セッション期限切れ | セッションとともに失われる（現行設定60分） |
| ログアウト／会員変更 | 解除。ログアウト時は既存Security設定でセッション破棄。認証成功時に保存会員IDと認証会員IDを比較し、異なる場合は同期的に解除。別会員は再適用 |

空カート時は現行の購入フローに従い `/cart` へ戻る。カート変更を契機にクーポンコードを即時削除しない。

## 2. 注文確認
- `GET /checkout/confirm` の既存MVC経路を使用する。
- セッションのクーポンコードを取得し、現在のカートで再検証・再計算する。
- 再検証失敗時はクーポンを解除し、カートへ戻してエラーを表示する。
- 成功時はクーポン名・割引額を確認画面に表示する。

## 3. 注文確定
- `POST /checkout/confirm` の既存MVC経路を使用する。
- DBトランザクション内でクーポンを最終再検証し、`coupons` → `user_coupon_usages` の順にロックする。
- 成功時は注文・注文スナップショット・利用回数更新を同一DBトランザクションに含める。
- DB処理の固定順序はロック順 `coupons` → `user_coupon_usages` とし、行確保は `ON CONFLICT DO NOTHING`、ロック後に上限を確認しカウントを一度だけ加算する。
- 注文INSERT・利用数加算・スナップショット保存の相互順序は、人間判断事項としてDD-04に記載する。順序確定まで実装開始不可。
- 再検証失敗時は注文・利用実績を確定せず、クーポンを解除する。戻り先・画面表示はAPI仕様の人間判断事項に従う。

## 4. ゲスト
- 個人上限ありのクーポンは利用不可。
- 個人上限なしのクーポンは利用可能。
- ゲストの会員別利用実績は保存しない。

## 5. 注文履歴
- 注文に保存した `applied_coupon_code`、`applied_coupon_name`、`coupon_discount_amount` を表示する。
- クーポンマスタを無効化しても過去注文のスナップショット表示は維持する。

## 6. CSRF・二重送信
- 既存のCSRF保護を維持する。
- 注文確定は既存ワンタイムトークンの仕組みを維持する。

## 7. 実装前の既存実装からFEAT-002仕様への変更（調査記録）

- `CartController` の注文確認GETにセッション取得・再検証・割引後表示を追加する。
- 注文確定POSTからセッションのクーポンコードを注文サービスへ渡し、失敗時に設計された画面遷移を行う。
- クーポン状態に適用時の会員IDを保持し、注文確認時・確定時に現在の会員IDと照合する。ログイン成功時も照合して会員変更なら解除する。
- カート画面・注文確認画面へ適用／解除UIおよびクーポン金額を接続する。
- 注文完了画面と注文履歴のsnapshot表示も取得・表示モデルへ接続する。履歴一覧と詳細の表示範囲は人間判断事項。
- 実装前のControllerにはクーポンAPI、クーポン表示項目、確定時のクーポン引き渡しがなかった。

## 8. 人間判断事項

- REST APIの各失敗時HTTPステータス。
