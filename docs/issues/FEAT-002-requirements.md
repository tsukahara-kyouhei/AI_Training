# FEAT-002: クーポン機能追加 要件定義書

## 1. 目的

-   新規および既存会員に向けた販促施策を機動的に実行し、コンバージョン率（CV）および再購入率を改善する。

## 2. 対象範囲

本機能追加に伴う影響範囲・対応画面は以下の通り。

-   **カート画面**: クーポンコードの入力、適用、適用解除
-   **注文確認～確定処理**:
    既存の注文確認・注文確定フローにおけるクーポンの再検証・再計算
-   **会員マイページ（注文履歴）**: 適用済みクーポンの表示
-   **キャンセル・返品**: 注文キャンセル・返品時のクーポン利用実績返還
-   **管理画面**:
    既存の管理システムでクーポンを登録・編集・有効化／無効化する想定。本リポジトリ内に既存管理画面は確認できないため、本FEAT-002ではWeb購入側の実装を対象とする。

## 3. 機能要件

### 3.1 クーポン適用・解除

-   クーポンコードの入力フォームをカート画面に設け、非同期APIで即時に適用可否を判定する。
-   1注文につき適用可能なクーポンは1件のみとする。
-   適用中のクーポンがある状態で別のクーポンを入力した場合は上書きせず、`COUPON_ALREADY_APPLIED`
    を返して既存クーポンの解除を促す。
-   クーポン適用状態は、既存の商品カート情報と整合する形で、カート画面から注文確定まで引き継ぐ。状態の保存場所は設計判断事項とし、本要件では指定しない。

### 3.2 割引計算ルール

-   割引種別は以下の2種類とする。
    1.  **定額割引**: 指定金額をクーポン対象商品の小計から差し引く。
    2.  **定率割引**: クーポン対象商品の小計に対して指定割合を差し引く。
-   定率割引は小数点以下を切り捨てる。
-   `max_discount_amount` は定率割引に適用する。定額割引には適用しない。
-   割引額はクーポン対象商品の小計を超えない。
-   送料、手数料はクーポンの割引対象外とする。
-   注文合計がマイナスにならないようにする。

### 3.3 クーポン適用条件

以下を記載順に判定する。

1.  クーポンコードが存在すること。
2.  `is_active = true` であること。
3.  既に別クーポンが適用されていないこと。
4.  現在日時が `valid_from` ～ `valid_to` の範囲内であること。
5.  会員条件を満たすこと。
6.  クーポン対象の商品またはカテゴリがカートに含まれていること。
7.  クーポン対象商品の小計が `min_purchase_amount` 以上であること。
8.  全体利用上限および会員別利用上限を超えていないこと。

対象商品・カテゴリはOR条件とする。
最小購入金額および割引計算の対象はクーポン対象商品の小計とする。

### 3.4 会員条件

-   現行実装で確認できる会員情報は `members` テーブルを使用する。
-   新規会員条件は、指定会員について注文状態が `completed`
    の過去注文が0件であることとする。
-   現行注文状態には `shipped` が存在しないため、新規会員判定に
    `shipped` は使用しない。
-   特定会員ランクによる条件は、現行会員データに対応するランク項目を確認できないため、本FEAT-002では実装対象としない。
-   `target_user_type` は `all` または `new` を使用する。
-   現行の注文フローではゲスト注文が可能である。クーポンのゲスト適用可否、および会員別利用上限付きクーポンのゲスト注文時の扱いは本要件では決定せず、設計判断事項とする。

### 3.5 注文時の再検証

-   既存の注文確認処理でクーポンを再検証する。
-   既存の注文確定処理でもクーポンを再検証する。
-   再検証で期限切れ、利用上限到達、対象条件不成立等が判明した場合はクーポンを解除し、金額を再計算する。
-   注文確認時の再検証NGはカート画面へ戻し、注文確定時の再検証NGは注文確認画面へ戻す。
-   注文確定時の利用実績更新・注文保存・クーポン再検証は、既存の
    `OrderService.placeOrder()`
    が使用するDBトランザクション内で整合させる。

### 3.6 履歴・スナップショット

注文確定時、以下を `orders` にスナップショット保存する。

-   `applied_coupon_code`
-   `applied_coupon_name`
-   `coupon_discount_amount`

クーポンマスタが変更・削除されても、過去の注文詳細からクーポン名・割引額を表示できること。

### 3.7 キャンセル・返品時の利用実績返還

-   注文キャンセル時は、クーポン利用実績の全体・会員別カウントを1件分減算する。
-   返品時も同様に減算する。
-   同一注文に対するキャンセル・返品処理の再実行で二重減算しない。
-   既存実装にはキャンセル／返品の実行経路が確認できないため、クーポン利用実績返還を接続するための処理をFEAT-002の実装対象とする。
-   既存注文状態に返品を表す状態や返品記録はない。返品の記録方法・状態遷移は設計判断事項とし、本要件では方式を指定しない。

## 4. 画面要件

### 4.1 カート画面

-   クーポンコード入力欄と「適用」ボタンを配置する。
-   適用中は割引額、クーポン名またはコード、解除ボタンを表示する。
-   適用中は入力フォームを非活性にする。
-   適用不可時はエラーコードに対応する具体的なメッセージを表示する。
-   解除時はクーポン表示を解除し、金額を再計算する。

### 4.2 注文確認画面

-   クーポン割引額を明細に表示する。
-   クーポン名を表示する。
-   再検証成功時の金額を表示する。
-   再検証失敗時はクーポンを解除してカートへ戻す。

### 4.3 会員マイページ（注文履歴詳細）

-   過去の注文詳細にクーポン名と割引額を表示する。
-   クーポンマスタが削除されても注文スナップショットを使用して表示できること。

## 5. データ要件

### 5.1 クーポンマスタ `coupons`

-   `id`
-   `code`
-   `name`
-   `discount_type`
-   `discount_value`
-   `max_discount_amount`
-   `min_purchase_amount`
-   `valid_from`
-   `valid_to`
-   `target_conditions`
-   `max_usage_total`
-   `max_usage_per_user`
-   `used_count_total`
-   `is_active`

PostgreSQLを使用する。日時は既存DBの日時型に合わせる。

### 5.2 会員別クーポン利用実績 `user_coupon_usages`

既存システムでは会員テーブルが `members`
であるため、会員を識別する外部キーは既存の会員IDに合わせる。

-   `id`
-   `member_id`
-   `coupon_id`
-   `usage_count`
-   `last_used_at`

`member_id` と `coupon_id` の組み合わせは一意とする。
`member_id` は `members.member_id` を参照する。ゲストの利用実績をどのように管理するかは本要件では決定しない。

### 5.3 `orders` の拡張

-   `applied_coupon_code`
-   `applied_coupon_name`
-   `coupon_discount_amount`

## 6. 非機能要件

-   **パフォーマンス**:
    クーポン適用判定のレスポンスタイム目標を300ms以内とする。
-   **排他制御**:
    注文確定時にクーポン全体利用上限および会員別利用上限の競合を防止する。
-   **トランザクション**:
    外部決済APIは既存システムに存在しないため、外部決済APIとの整合性を前提とした二段階トランザクションは使用しない。既存の
    `OrderService.placeOrder()`
    のDBトランザクション内でクーポン再検証、利用実績更新、注文保存を整合させる。
