# FEAT-002: クーポン機能追加 要件定義書（最終版）

## 1. 目的
- 新規および既存会員向け販促施策を実行し、CVおよび再購入率を改善する。

## 2. 対象範囲
- カート画面でのクーポンコード入力・適用・解除。
- 注文確認・注文確定での再検証・再計算。
- 注文履歴でのクーポンスナップショット表示。
- クーポンマスタの登録・編集・有効化／無効化は購入者向け機能の対象外とする。リポジトリ内に管理側の登録経路を確認できないため、登録機能をFEAT-002へ含めるかは人間判断事項。

## 3. 機能要件

### 3.1 適用・解除
- `POST /api/cart/coupon` で即時判定する。
- 1注文1クーポン。
- 別クーポンが適用済みなら `COUPON_ALREADY_APPLIED`。
- 適用状態はセッションに保存する。

### 3.2 割引
- 定額、定率の2種類。
- 定率はFLOOR。
- 最大割引額は定率のみ。
- 最終割引額は対象小計を超えない。
- 金額は整数円。
- 送料・手数料は割引対象外。
- 税額はクーポン割引後の商品小計と組立費を基準に算出する。
- 送料無料判定はクーポン適用前のカート金額で行い、現行の5,000円（税込み課税対象小計）以上なら無料、それ未満なら800円とする。クーポン割引後に送料無料条件を再判定しない。
- 注文合計は `割引後商品小計 + 組立費 + 税額 + 送料` とする。
- 既存の注文ヘッダー `subtotal_amount` は商品割引前の商品小計を保持し、割引額は `coupon_discount_amount`、合計は割引後金額から算出する。
- 注文明細にはクーポン対象商品の商品小計に比例してクーポン割引額を配賦する。整数円の配賦端数は剰余の大きい明細から1円ずつ配り、同率の場合はカート内の明細順とする。明細小計は割引前の値を保持し、配賦割引額を別項目に保存する。
- 明細税額は「割引前明細小計 - 配賦割引額」に組立費を含む課税対象金額を基準に、既存税率・切り捨てで明細単位に算出する。ヘッダー税額との端数差を埋める調整は行わず、ヘッダー税額を注文合計計算の税額とする。

### 3.3 条件
- 有効期間内。
- 対象商品の小計が最低購入金額以上。
- 対象カテゴリまたは対象商品が存在。
- カテゴリ条件と商品条件はOR。
- `target_user_type` は `all` / `new`。`new` はcompleted注文0件。
- 全体利用上限を管理。
- 会員別利用上限を管理。
- 会員別上限ありのクーポンはゲスト利用不可。未設定クーポンはゲスト利用可。
- `target_conditions` は `allowed_category_ids`（`desk` / `chair` / `storage` の文字列配列）、`allowed_product_ids`（正の整数配列）、`target_user_type`（`all` / `new`）の3キーを必須とする。null、欠落、不正JSON、型不正、許容値外は登録時に拒否する。未知キーおよび存在しない商品IDの登録可否は人間判断事項。

### 3.4 再検証
- 注文確認表示時と注文確定時に再検証する。
- 失敗時はクーポンを解除し、金額を再計算する。
- 確認時失敗はカートへ戻す。確定時失敗は確認画面へ戻す。
- 商品追加・削除・数量変更・カート全削除後もセッション上のクーポンコードは保持し、注文確認時に現在のカートで再検証する。カートが空なら既存フローどおりカート画面へ戻す。
- 会員が変更された場合はセッション上のクーポンを解除し、別会員で利用する際は再適用する。
- セッションにはクーポンコードと適用時の会員IDを関連付け、ゲスト時は会員IDをNULLとする。認証後の会員IDが異なる場合は解除する。
- セッション失効に伴いクーポン状態も失われる。現行セッションタイムアウトは60分。

### 3.5 スナップショット
注文確定時に以下を保存する。
- `applied_coupon_code`
- `applied_coupon_name`
- `coupon_discount_amount`

## 4. 画面

### 4.1 カート
クーポン入力、適用、解除、クーポン名、割引額、不適用理由を表示する。

### 4.2 注文確認
クーポン名・割引額を表示する。

### 4.3 注文履歴
注文スナップショットからクーポン名・割引額を表示する。

## 5. データ

### 5.1 coupons
`id`, `code`, `name`, `discount_type`, `discount_value`, `max_discount_amount`, `min_purchase_amount`, `valid_from`, `valid_to`, `target_conditions`, `max_usage_total`, `max_usage_per_user`, `used_count_total`, `is_active`, timestamps。

`target_conditions` はJSONB。登録時に構造検証する。

### 5.2 user_coupon_usages
`id`, `member_id`, `coupon_id`, `usage_count`, `last_used_at`, timestamps。`member_id + coupon_id` を一意制約とし、FKはRESTRICT/NO ACTION。

### 5.3 orders
`applied_coupon_code`, `applied_coupon_name`, `coupon_discount_amount` を追加する。

注文明細には `line_coupon_discount_amount` を追加し、各明細への配賦額を保存する。`line_subtotal` は割引前小計を維持し、明細税額は配賦割引後の課税対象額から計算する。

## 6. キャンセル・返品
- キャンセルは `cancelled` への状態遷移で処理する。
- 返品は `returned` 状態を追加する。
- 返品は注文単位、部分返品なし。
- 状態遷移成功時に利用実績を1件返還する。
- 再実行時の二重返還を防止する。
- 注文状態ごとのキャンセル可能・返品可能な遷移元は人間判断事項とする。既存の状態一覧だけでは遷移規則を一意に定められない。

## 7. 非機能
- カート適用判定の目標レスポンスタイムは300ms以内。
- 注文確定時の全体・会員別利用上限は悲観ロックで競合制御する。
- ロック順序は `coupons` → `user_coupon_usages`。
- 既存のオフライン決済を使用し、外部決済APIは追加しない。

## 8. 人間判断事項

| 項目 | 判断が必要な内容 | 根拠 |
|---|---|---|
| 状態遷移 | `received`、`awaiting_payment`、`processing`、`completed` からのキャンセル／返品可否、および `cancelled` と `returned` の相互遷移可否 | 既存DBは状態値を制約するだけで、許可遷移を定義していない |
| クーポン登録 | `target_conditions` 登録時検証を担う管理機能をFEAT-002に含めるか | 現行コードにクーポン管理側の登録経路を確認できない |
| API応答 | RESTエラーごとのHTTPステータスと、MVC注文確定失敗時の応答・確認画面への復帰方法 | 現行MVCにはクーポン固有エラー経路がなく、REST APIも未実装 |
| API形状 | 適用API成功JSONの完全なフィールド名・型、および `subtotal`／`total` の税・送料包含 | 既存APIに一致する既存契約がない |
| 注文履歴画面 | snapshot表示を一覧・詳細のどちらに出すか | 要件は注文履歴とだけ定義し、画面粒度を指定していない |
| DDL詳細 | 新設列の文字列長、割引率の許容範囲・精度、日時境界の包含規則、利用上限値NULLの意味、各INDEX・CHECKの完全な定義 | 現行DBの類似列定義から一意に確定できない |
| 注文確定順序 | ロック・再検証・注文INSERT・利用数加算・スナップショット保存の完全な順序 | 各順序で同一トランザクションを構成でき、既存実装から一意に選べない |
| target_conditions | 未知キーおよび存在しないproduct_idの登録可否 | 構造不正拒否の決定だけではこの2ケースの扱いは定まらない |
