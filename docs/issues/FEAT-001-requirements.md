# FEAT-001 商品キーワード検索機能改善 要件定義書

## 1. 概要

### 1.1 対象機能

| 項目 | 内容 |
|------|------|
| 機能ID | FEAT-001 |
| 機能名 | 商品キーワード検索機能改善 |
| 対象画面 | SRCH002 キーワード検索結果 (`/products/search`) |
| 作成日 | 2026-03-16 |

### 1.2 背景・目的

現状のキーワード検索画面（SRCH002）では以下の課題がある。

- 商品コードの検索に中間一致を用いているため、コードの一部に過ぎない数字が意図せず一致してしまう誤検索が発生しうる。
- 説明文・シリーズバリエーション名が検索対象外であり、ユーザーが期待するヒット率を得られない。
- 全角・半角の違いにより同一の意図を持つ入力が異なる検索結果になる。
- テイストによる絞り込みができず、カテゴリ一覧画面と比べて絞り込みの利便性が劣る。

本課題では上記を解消し、検索精度と利便性を向上させる。

|--------------|-----------------|---------|------|
| 商品名 | `products.product_name` | 中間一致 (ILIKE) | 大文字小文字区別なし |
| 商品コード | `product_variants.product_code` | 中間一致 (ILIKE) | 大文字小文字区別なし |

### 2.2 現状の絞込条件

| 絞込条件 | 対応状況 |
|---------|---------|
| 在庫あり | 対応済み |
| 価格帯 | 対応済み |
| カラー | 対応済み |
| テイスト | **未対応** |

### 2.3 現状のキーワード変換処理

- `ProductRepository#toKeywordLike` にて入力キーワードを `%keyword%` 形式に変換
- 大文字小文字区別なし（PostgreSQL ILIKE による）
- 全角・半角の正規化処理なし

## 3. 機能要件

### 3.1 検索対象フィールドの追加

キーワード検索の対象フィールドを以下のとおり拡張する。

| No | 検索フィールド | 対象テーブル/カラム | 一致方式 |
|----|--------------|-----------------|---------|
| 1 | 商品名 | `products.product_name` | 部分一致 |
| 2 | シリーズバリエーション名 | `products.variation_name` | 部分一致 |
| 3 | 説明文 | `products.description` | 部分一致 |
| 4 | 商品コード | `product_variants.product_code` | 完全一致 **または** 前方一致 |

> **商品コードを中間一致としない理由**：コードに含まれる数字の一部が意図せず別商品コードとマッチするため、完全一致または前方一致に限定する。

> **実装方式（案B採用）**：ユーザーへの選択 UI は提供しない。SQL では「完全一致 OR 前方一致」を常に OR 条件で評価する（例：`product_code = #{keyword} OR product_code ILIKE #{keyword}||'%'`）。

### 3.2 大文字・小文字の区別なし検索

- 英字の大文字・小文字を区別せずに検索できること。
- 例：`desk` と `DESK`、`A100` と `a100` は同一として扱う。
- 現状と同様にPostgreSQL の `ILIKE` 演算子で対応する。

### 3.3 全角・半角の区別なし検索

検索入力時および検索対象データに対し、以下の文字種について全角・半角を正規化してから比較すること。

| 文字種 | 正規化方向 | 例 |
|-------|-----------|---|
| 数字 | 全角 → 半角 | `１２３` → `123` |
| 英字 | 全角 → 半角 | `Ａ` → `A` |
| カタカナ | 半角 → 全角 | `ｵﾌｨｽ` → `オフィス` |

> **正規化の適用範囲（方式A採用）**：検索入力値（キーワード）のみを正規化して検索する。DB 格納値はカタカナ全角・英数字半角で統一されていることを前提とし、DB 側に変換ロジックを持たせない。

> **前提となる DB 格納形式**：カタカナは全角、英字・数字は半角で格納されていること（アプリケーションによる入力正規化で担保済み）。

> **ひらがな・漢字・記号等**は正規化対象外とし、現状どおりの扱いとする。

### 3.4 テイスト絞込の追加

検索結果画面（SRCH002）の絞込条件に「テイスト」を追加する。

#### 3.4.1 テイスト絞込の仕様

- 各カテゴリ一覧（SRCH003 デスク、SRCH004 チェア、SRCH005 ストレージ）の絞込条件「テイスト」と同じ仕様とする。
- テイストのマスタデータおよびUIコンポーネント（チェックボックス一覧）はカテゴリ一覧と共通仕様とする。
- 複数テイストを選択した場合は OR 条件（いずれかに該当）で絞り込む。

**選択肢ソース（案A採用）**：`ProductFilterOptionsBundle` に新フィールド `searchTasteOptions`（`List<CategoryFilterOption>`）を追加し、`ProductFilterOptionService` でテイスト一覧を取得・設定する。検索結果画面ではこの `searchTasteOptions` をテイスト絞込の UI 選択肢として使用する。

**モデル格納方式（案A採用）**：検索画面から受け取ったテイスト ID は `ProductSearchCondition` の新フィールド `List<Integer> tasteIds` に格納する。既存の `ProductCategoryFilter` の各テイストフィールドは変更しない。

#### 3.4.2 カテゴリ横断時の動作

キーワード検索はカテゴリを横断するため、テイスト情報は各カテゴリの属性テーブル（デスク・チェア・ストレージ）に分散して持つ。絞込動作は以下のとおりとする。

| カテゴリ指定状況 | テイスト絞込の動作 |
|--------------|-----------------|
| カテゴリ未指定（全カテゴリ横断） | デスク・チェア・ストレージ属性テーブルのいずれかにおいて指定テイストに合致する商品を対象とする |
| カテゴリ指定あり | 対象カテゴリの属性テーブルのテイストで絞り込む（現状のカテゴリ一覧と同仕様） |

**SQL・フラグ設計（案A採用）**：`ProductRepository#buildSearchParams` に新フラグ `hasSearchTasteFilter` を追加する。カテゴリ横断時（`categoryId` が null）かつテイストが選択されている場合に `true` となる。`ProductMapper.xml` には新フラグメント `SearchTasteFilter` を追加し、デスク・チェア・ストレージ属性テーブルを OR 結合する SQL で横断絞込を実現する。既存の `hasDeskFilter`・`hasChairFilter`・`hasStorageFilter` の条件判定は変更しない。

#### 3.4.3 テイストマスタ

現状のテイストマスタ（各カテゴリ共通の値セット）を使用する。

| テイスト名 |
|----------|
| ベーシック |
| カジュアル |
| シンプル |
| モダン |
| ナチュラル |

**テイストマスタ ID の一意性保証（案A採用）**：`desk_tastes`・`chair_tastes`・`storage_tastes` の各テーブルにおいて、同一テイスト名は常に同一の `taste_id` を持つことを**運用仕様として保証**する。以後、これら 3 テーブルへの行追加・削除・ID 変更は本保証を維持する形で行うこと。共通テイストマスタテーブルの新設は行わない。

### 3.5 現状踏襲事項

以下の機能・仕様については変更しない。

- 在庫あり絞込
- 価格帯絞込
- カラー絞込
- ソート順（おすすめ順、新着順、価格昇順・降順）
- ページネーション（1ページあたり15件）
- URL パラメータ構造（`q`、`inStockOnly`、`priceBand`、`color`、`sort`、`page`、`size`）
- 販売期間フィルタ（`sale_start_at` / `sale_end_at`）

## 4. 非機能要件

### 4.1 性能要件

| 項目 | 目標値 |
|-----|-------|
| 検索対象商品数 | 最大 1,000 件程度 |
| 一覧初回表示レスポンスタイム | 95 パーセンタイルで 2 秒以内 |

### 4.2 検索精度・品質要件

- テキスト正規化（全角・半角変換）はアプリケーション層（Java サービス層）で実施し、DB 側に変換ロジックを持たせない。
- 正規化後のキーワードが空文字になる場合は、キーワードなしと同等の扱いとし全件を対象とする。

### 4.3 インデックス設計

`products.description` は `text` 型（長文）のため、ILIKE による中間一致検索に B-tree インデックスが適用されない。性能目標（95%ile 2秒以内）の達成に向け、以下の対応を行う。

| 対象カラム | インデックス種別 | 優先度 | 備考 |
|-----------|--------------|-------|------|
| `products.description` | GIN（`pg_trgm` 拡張） | **必須** | 長文テキストの中間一致高速化 |
| `products.product_name` | GIN（`pg_trgm` 拡張） | 推奨 | 既存 ILIKE の高速化 |
| `products.variation_name` | GIN（`pg_trgm` 拡張） | 推奨 | 新規追加フィールドの高速化 |

> `pg_trgm` 拡張が未導入の場合は `CREATE EXTENSION IF NOT EXISTS pg_trgm;` の実行が必要。DDL 変更として `sql/schema/` 配下のマイグレーションスクリプトに含める。

> 商品数 1,000 件規模であれば GIN インデックスなしでも性能目標を満たせる可能性があるが、`description` の長文特性を考慮し必須対応とする。

## 5. 画面要件

### 5.1 対象画面

SRCH002 キーワード検索結果 (`/products/search`)

### 5.2 絞込条件 UI 変更

| 絞込条件 | 変更前 | 変更後 |
|---------|-------|-------|
| 在庫あり | あり | 変更なし |
| 価格帯 | あり | 変更なし |
| カラー | あり | 変更なし |
| テイスト | **なし** | **追加** |

- テイストの UI コンポーネント（チェックボックス一覧形式）はカテゴリ一覧画面のテイスト絞込と同一のレイアウト・スタイルとする。
- クエリパラメータ名は `taste`（複数選択可）とする。
- **モバイル版絞込モーダル（`modal-filters-search`）は本課題の対象外**とする。現在の「簡易版 UI 表示中」プレースホルダーは変更しない。

### 5.3 テイスト選択状態の引き継ぎ

テイストを選択した状態で以下の操作を行っても、テイスト選択状態が維持されること。

| 操作 | 対象箇所 | 対応内容 |
|-----|---------|--------|
| 並び順変更 | 並び順フォームの hidden フィールド群 | `name="taste"` hidden 追加 |
| 表示件数変更 | 同上 | 同上 |
| 前へ／次へ ページ遷移 | ページネーション `th:href` | `taste=${selectedTasteIds}` 追加 |
| 先頭ページリンク | ページネーション 1ページ目リンク | 同上 |
| 末尾ページリンク | ページネーション 最終ページリンク | 同上 |
| 中間ページリンク | ページネーション ウィンドウ内リンク | 同上 |
| リセットリンク | 絞込フォーム内 `a.btn` リセット | `taste` パラメータを含めない（リセット正常動作） |

## 8. 設計・実装上の制約事項
