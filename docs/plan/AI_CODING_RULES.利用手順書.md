# AI_CODING_RULES.md 利用手順書

## この手順書の見方

AIに開発を依頼するときは、**共通ルールを読み込ませ、作業段階に合ったプロンプトを使います。**

**基本の流れ**

調査・計画 → 人が確認 → 実装 → テスト → 最終レビュー → 人が最終確認

---

## 1. このファイルは何？

`AI_CODING_RULES.md` は、AIにソースコードの作成・修正・テスト・レビューを依頼するときの**共通ルール**です。

このルールによって、次の点を統一します。

- 既存のソースコードやDB定義を調査してから変更する
- 要件・設計にない仕様変更を勝手に行わない
- 分からないことを推測で決めない
- テストを実行し、実際の結果を根拠とともに報告する
- 変更内容と影響範囲を人が確認できるようにする

## 2. ファイルの役割と利用順序

最初にこの利用手順書で全体の流れを把握し、実際の開発では `AI_CODING_RULES.md` と作業段階に合った工程別プロンプトを組み合わせて使用します。

### ファイルの役割

**共通ルールの正本**

- `AI_CODING_RULES.md`
  - すべての工程でAIが守る共通ルールを定義します。
  - 共通ルールを変更するときは、このファイルを正本として更新します。

**工程別プロンプト**

- `01_実装前調査プロンプト.md`：要件・設計、既存コード、DB、SQL、Mapper、API、テストなどを調査し、実装方針を整理します。調査段階では対象ファイルを変更させません。
- `02_実装プロンプト.md`：人が確認した調査結果と実装方針に沿って、必要な範囲に絞って実装します。
- `03_テストプロンプト.md`：テスト計画と実装内容に基づき、テストを追加・実行し、結果と根拠を整理します。
- `04_最終レビュー・修正プロンプト.md`：要件・設計・実装・DB/API・テストの整合性を横断的に確認し、必要な修正を行います。

**補助資料**

- `05_人が読みやすい出力ルール・報告テンプレート.md`：報告の見せ方やテンプレートを確認するための資料です。通常、毎回AIに渡す必要はありません。
- 要件定義書・設計書：今回の機能で満たすべき要件と仕様を確認するために使用します。共通ルールとは別に管理します。

### 推奨する利用順序

1. **調査・計画：** `AI_CODING_RULES.md` ＋ `01_実装前調査プロンプト.md`
2. **人による確認：** 調査結果、変更範囲、影響先、テスト方針を確認し、不明点や判断事項を解消します。
3. **実装：** `AI_CODING_RULES.md` ＋ `02_実装プロンプト.md`。調査結果と確認済みの方針を引き継ぎます。
4. **テスト：** `AI_CODING_RULES.md` ＋ `03_テストプロンプト.md`。調査時のテスト計画と実装内容を引き継ぎます。
5. **最終レビュー・修正：** `AI_CODING_RULES.md` ＋ `04_最終レビュー・修正プロンプト.md`。前工程の結果と現在の成果物を照合します。
6. **人による最終確認：** Git差分、変更ファイル、テスト実行ログ、未解決事項、最終成果物を確認します。

各工程の結果は次の工程に引き継ぎます。AIの報告だけで完了と判断せず、実ファイルや実行ログなどの根拠を確認してください。

> **運用の原則：** 共通ルールの正本は `AI_CODING_RULES.md` です。工程別プロンプトには各工程固有の作業と報告項目を記載し、共通ルールの本文を重複して管理しないでください。

## 3. 基本的な使い方

各工程の結果を次の工程に引き継ぎ、**人が確認してから次へ進む**ことが重要です。


### 共通ルールファイルの適用方法

`AI_CODING_RULES.md` は、すべての工程で共通して適用する開発ルールです。

- **AIがプロジェクト内の `AI_CODING_RULES.md` を参照できる場合：** プロジェクト内に配置しておけば、各フェーズで毎回ファイルを添付する必要はありません。ただし、各工程の作業開始時にAIがルールを参照できることを確認してください。
- **AIがプロジェクト内のファイルを参照できない場合：** 各フェーズの作業依頼時に `AI_CODING_RULES.md` を添付するか、ルールの内容を提示してください。

工程別プロンプトは、実行するフェーズに応じて使い分けます。共通ルールファイルと工程別プロンプトは役割が異なるため、混同しないでください。

### STEP 1　調査・計画

**使用ファイル**

- `AI_CODING_RULES.md`
- `01_実装前調査プロンプト.md`

**AIに依頼すること**

要件・設計と既存実装を調査し、変更対象・実装方針・テスト方針を整理させます。この段階ではファイルを変更させません。

### STEP 2　人が調査結果を確認

**人が確認すること**

- 要件の理解に誤りがないか
- 変更範囲と影響先が適切か
- テスト方針に問題がないか
- 不明点や人の判断が必要な点が残っていないか

問題があれば解消してから実装へ進みます。

### STEP 3　実装

**使用ファイル**

- `AI_CODING_RULES.md`
- `02_実装プロンプト.md`

**AIに依頼すること**

STEP 1の調査結果と、STEP 2で確認した方針を引き継ぎ、必要な範囲に絞って実装させます。

### STEP 4　テスト

**使用ファイル**

- `AI_CODING_RULES.md`
- `03_テストプロンプト.md`

**AIに依頼すること**

実装内容とテスト計画を引き継ぎ、必要なテストを追加・実行させます。実行結果とログも確認します。

### STEP 5　最終レビュー・修正

**使用ファイル**

- `AI_CODING_RULES.md`
- `04_最終レビュー・修正プロンプト.md`

**AIに依頼すること**

調査・実装・テストの結果を引き継ぎ、要件・設計との整合性や不要な変更がないか確認させます。修正した場合は、関連テストを再実行させます。

### STEP 6　人が最終確認

**人が確認すること**

- Git差分と変更ファイル
- テスト結果と実行ログ
- 未解決事項と人の判断が必要な事項
- 最終成果物が要件・設計を満たしているか

### 工程ごとの確認ポイント

**調査後**

要件・設計の理解、変更対象、影響範囲、テスト方針、推測の有無を確認します。

**実装後**

変更ファイル、要件・設計との対応、不要な変更、既存機能への影響を確認します。

**テスト後**

PASS / FAIL、未実行・実行不可のテスト、実行ログ、テスト不足の有無を確認します。

**最終レビュー後**

Git差分、仕様との整合性、未解決事項、最終成果物を確認します。

> **注意：** いきなり「実装して」と依頼しないでください。先に調査・計画を行い、その結果を人が確認することで、仕様の誤解や不要な変更を防ぎます。

## 4. 01_実装前調査プロンプト

実装を始める前に使用します。対象の機能名と要件定義書・設計書を指定し、関連する既存コード、DB定義、SQL、Mapper、API、設定、既存テストを調査させます。

**この工程では、ソースコード・SQL・DB定義・設定・テストコードを変更させません。**

### 調査後に人が確認すること

- 要件・設計の理解が正しいか
- 変更するファイルと変更しないファイルが明確か
- DB・API・画面・既存機能への影響を把握しているか
- テスト対象と期待結果が具体的か
- 推測で仕様を決めていないか
- 実装を開始できる状態か

実装開始に必要な情報が不足している場合は、その理由を整理し、人の判断や情報の補完を行ってから進めます。

## 5. 02_実装プロンプト

01の調査結果と、人が確認した実装方針に基づいて使用します。

- 変更は必要最小限にする
- 既存仕様を無断で変更しない
- 要件・設計にない機能を追加しない
- 無関係なリファクタリングをしない
- 既存テストを削除しない
- 作業開始前から存在する変更や未追跡ファイルを保護する

実装後は、変更ファイル、変更内容、要件・設計との対応、既存機能への影響、実行した確認内容を報告させます。

## 6. 03_テストプロンプト

実装後に使用します。01のテスト計画・期待結果と、02の変更内容を引き継ぎ、既存テストを確認したうえで必要なテストを追加・実行します。

### 主なテスト観点

- 正常系・異常系・境界値
- NULL・空文字・空白・不正値
- DB処理・SQL・API処理
- 変更箇所と関連する既存機能への影響
- テストデータ、対象スキーマ、環境設定の安全性

### テスト結果の見方

**PASS**

テストを実行し、期待結果と実際の結果が一致した。

**FAIL**

テストを実行したが、期待結果と実際の結果が一致しなかった。

**NOT RUN**

テストを実行していない。

**NOT APPLICABLE**

今回の変更ではテスト対象外である。

**BLOCKED**

実行を試みたが、環境・設定などの理由で実行できなかった。

> **注意：** 実行していないテストを `PASS` として報告させないでください。テスト実行ログなどの根拠を確認し、`FAIL` または `BLOCKED` の場合は原因・影響・次の対応を確認します。

## 7. 04_最終レビュー・修正プロンプト

実装・テスト後に使用します。01〜03の結果と現在の成果物を照合し、要件・設計・画面/API/DB・実装・テストの整合性を確認します。

### 主な確認内容

1. 要件を満たし、設計と一致しているか
2. 既存機能への影響を確認しているか
3. コーディング規約に違反していないか
4. SQL・DB定義・API仕様と矛盾していないか
5. テストが十分で、結果に根拠があるか
6. 不要なファイル変更や仕様変更が入っていないか

問題は、原則として **「問題箇所 → 根拠 → 重要度・影響 → 修正方針」** の順で整理します。仕様変更やDB/API仕様変更など、人の判断が必要な内容は勝手に修正させません。修正した場合は関連テストを再実行します。

## 8. AIの回答がおかしいとき

### 調査せずに実装した場合

```text
実装を中止してください。
既存ソースコード、DB定義、SQL、Mapper、関連テストを実ファイルで調査し、調査結果と実装方針を報告してください。
この指示を受けている段階では、ソースコードや設定を変更しないでください。
推測で仕様を決めないでください。
```

### 仕様を勝手に変更した場合

```text
今回の変更で仕様が変わっていないか確認してください。
「変更前の仕様 → 今回の変更内容 → 要件・設計上の根拠 → 問題点」を整理してください。
仕様変更が必要な場合は修正を中止し、人の判断が必要な事項として報告してください。
```

### テストを実行していない場合

```text
テストを実行していない状態を完了扱いにしないでください。
実行可能な関連テストを実行し、PASS / FAIL / NOT RUN / NOT APPLICABLE / BLOCKED で分類してください。
実行コマンド、結果、ログなどの根拠を示してください。FAILまたはBLOCKEDの場合は原因と次の対応も説明してください。
```

## 9. 人が最終確認するポイント

### 実装前

- 要件・設計の理解と変更範囲が適切か
- 仕様の矛盾や人の判断が必要な事項が明示されているか
- テスト対象・期待結果が具体的か

### 実装後

- Git差分と変更ファイル
- 不要な変更や、作業開始前からあった変更との混同がないか
- API・DB・SQL・設定の変更内容

### テスト後

- PASS / FAILの内容と実行ログ
- NOT RUN / BLOCKED の有無と理由
- テスト不足やテストデータによる影響がないか
- 実行されていないテストをAIがPASSとしていないか

### 最終確認

- 要件を満たしているか
- 設計と一致しているか
- 既存機能への影響を確認しているか
- 不要な変更がないか
- 未解決事項と人の判断が必要な事項が明確か

## 10. これだけ覚えればOK

1. `AI_CODING_RULES.md` で共通ルールを確認する。
2. `01_実装前調査プロンプト.md` で先に調査させる。
3. 人が調査結果と方針を確認する。
4. `02_実装プロンプト.md` で実装させる。
5. `03_テストプロンプト.md` でテストする。
6. `04_最終レビュー・修正プロンプト.md` で最終レビューする。
7. 人がGit差分・テストログ・最終成果物を確認する。

共通ルールは `AI_CODING_RULES.md` に集約し、工程別プロンプトには各工程固有の作業と報告項目を記載します。同じルールを複数ファイルで別々に管理することを防ぎます。

**AIにすべてを任せるのではなく、AIに調査・実装・テスト・レビューをさせ、人が各段階で判断することが基本です。**
