# 04_最終レビュー・修正プロンプト

## 目的
01〜03の引き継ぎ情報と実際の成果物・Git差分・テスト証拠を照合し、重大な問題を確認する。必要な場合だけ、根拠に基づき最小限で修正する。

## コピペ用プロンプト

```text
以下の共通ルールと指示に従って最終レビューしてください。

【共通ルール】
- AI_CODING_RULES.md（実際のファイル名に合わせる）

【今回の対象】
- 機能ID：[対象機能のIDを記載。未採番の場合は「なし」]
- 機能名：[対象の機能名を記載]
- 要件・設計書：[対象となる要件定義書・設計書のファイルパスを記載。なければ「なし」]
- 01調査結果：[01の調査結果・引き継ぎ資料のファイルパスまたは内容を記載]
- 02実装結果：[02の実装結果・変更ファイル一覧のファイルパスまたは内容を記載]
- 03テスト結果：[03のテスト結果・実行ログ・未実施テストの情報を記載]
- 補足：[レビュー時の制約や補足事項を記載。なければ「なし」]

【レビュー手順】
1. 01〜03の引き継ぎと、現在のファイル・Git差分・テスト結果を照合する。
2. 作業前から存在した変更・未追跡ファイルを識別し、今回の変更と混同しない。
3. 要件→設計→画面/API/DB→実装→テストの整合性マトリクスを確認し、不一致・未確認を洗い出す。
4. 要件・設計、実装、DB / SQL、テスト結果の整合性を確認する。
5. 03で確認済みのテストは、修正・差分・証拠不足など再確認する根拠がない限り繰り返さない。
6. 問題があれば、修正前に問題箇所、根拠、重要度、影響、修正方針を整理する。
7. 仕様変更、DB/API変更、セキュリティ判断、対象範囲拡大が必要な問題は勝手に修正しない。
8. 要件・承認済み設計の範囲内で直せる問題だけ、必要最小限で修正する。
9. 修正した場合は影響範囲を追跡し、該当テストと関連回帰テストを再実行する。
10. 見栄えや好みだけを理由にリファクタリングしない。
11. 重大な未確認事項が残る場合は、レビュー完了と断定しない。

【確認項目】
- 要件・承認済み設計との一致
- 画面・API・DB・SQL・Mapper・実装・テストの横断整合性
- 既存機能、共通処理、API、SQLへの影響
- Java規約、例外処理、ログ、NULL / 空文字 / 空白
- DB制約、JOIN、一覧取得と件数取得の条件一致、ページング、ソート
- 入力検証、SQLインジェクション、認証・認可、機密情報のログ出力（該当範囲）
- テスト証拠、異常系・境界値・回帰・トランザクション（該当範囲）
- Git差分、変更範囲、作業前からの差分保護
- 設定、互換性、データ移行、性能（今回の変更に関係する範囲）

【重要ルール】
- 実際に確認できていない内容を確認済みとしない。
- 実行していないテストをPASSとしない。
- 不明な仕様を推測して修正しない。
- テストを削除・無効化してPASSにしない。
- 既存の作業差分を上書き・破棄しない。
- Git add / commit / pushは明示的な依頼がない限り実行しない。
- DB接続先・スキーマを確認し、通常利用データを不用意に変更・削除しない。

【報告形式】

## 1. 総合確認
| 項目 | 結果（PASS/FAIL/NOT RUN/NOT APPLICABLE/BLOCKED） | 根拠 |
|---|---|---|
| 要件・設計 | | |
| 成果物横断の整合性 | | |
| 既存機能への影響 | | |
| コード品質・セキュリティ | | |
| DB / SQL / Mapper | | |
| テスト証拠 | | |
| 変更範囲・Git差分 | | |

## 2. 問題一覧
| # | 箇所 | 根拠 | 重要度 | 影響 | 修正方針 |
|---|---|---|---|---|---|

問題がない場合も、確認した範囲と根拠を記載する。

## 3. 修正内容
| ファイル | 修正内容 | 理由 | 影響範囲 |
|---|---|---|---|

修正がない場合は「修正なし」と記載する。

## 4. 修正後のテスト結果
| テスト | 結果区分 | 実行内容 | 終了コード・件数 | 根拠 |
|---|---|---|---|---|

修正なしの場合は、03の結果を再利用したのか、追加確認したのかを区別する。

## 5. 横断整合性の最終状態
| 項目 | 判定 | 根拠・残存事項 |
|---|---|---|

## 6. 最終変更ファイル
| ファイル | 今回の最終変更 | 作業前から存在した差分との区別 |
|---|---|---|

## 7. 未確認・未実施・残存リスク
| 項目 | 理由 | 影響 | 対応要否 |
|---|---|---|---|

## 8. 人による最終確認ポイント
- 仕様判断が必要な箇所：
- 未実施・BLOCKEDのテスト：
- 重要な差分：
- DB / API / セキュリティ上の残存リスク：

## 9. 作業終了ゲート
以下を「完了 / 未完了 / 対象外」で判定する。
- 要件・設計・実装・テストの整合性
- 今回の変更差分
- 必要なテストと証拠
- 未実施・未確認事項の明記
- 重大な未解決事項の有無
- 作業前からの差分の保護

最終結果：
- レビュー完了・修正なし
- レビュー完了・修正済み（関連テスト確認済み）
- 修正後も問題あり
- 仕様確認が必要
- テスト実行BLOCKED
- 重大な未確認事項あり

## 10. 最終引き継ぎ
- 最終変更ファイル：
- 実行したテスト・証拠：
- 全体テストの実施有無：
- 未実施 / BLOCKED：
- 残存リスク：
- Git操作（add / commit / push）の実施有無：

## 11. 共通の出力ルール
出力の見やすさ、作業状態の表記、根拠の示し方、テスト結果の表記は、`AI_CODING_RULES.md` 第41章「人が読みやすい出力・報告ルール」に従ってください。このプロンプト内の工程固有の報告項目は省略せず、共通ルールと矛盾しない形で維持してください。

完了条件を満たしたら作業を終了してください。好みや見栄えだけを理由に変更を追加しないでください。
```
