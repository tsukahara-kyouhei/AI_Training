## 2. 全設計書への統一事項
- `member_id` / `memberId` に統一。
- 利用実績UPSERTは `ON CONFLICT DO NOTHING` による行確保後、`FOR UPDATE` でロックして1回だけ加算。
- ロック順序は `coupons` → `user_coupon_usages`。
- 注文確認・確定は既存MVCの `GET /checkout/confirm`、`POST /checkout/confirm`。
- REST APIはカートの適用・解除のみ。
- 注文スナップショットはコード・名前・割引額の3項目。
- 定率割引は `FLOOR`、最大割引額は定率のみ、最終割引額は対象小計を上限とする。
- 0円の対象商品は対象条件成立。最低購入金額は別判定。
- クーポン適用状態はセッション保持、確認・確定時にサーバー再検証。
- 既存オフライン決済を使用し、外部決済APIは追加しない。
- キャンセル／返品の返還は二重実行を防止する。

## 3. 今回追加された確定事項

| No | 確定事項 | 設計への反映 |
|---:|---|---|
| 1 | 税計算基準はクーポン割引後商品小計 | 商品小計から割引後小計を求め、組立費を加えた課税対象額で税計算する |
| 2 | 送料無料判定基準は割引前 | 現行の割引前課税対象小計（税込み）5,000円以上無料／未満800円を維持し、割引後再判定しない |
| 3 | 税額の割引後基準 | ヘッダー税額は割引後基準。明細割引は対象商品小計比で配賦し、明細税は既存税率・切り捨てで再計算。明細単位の端数差は追加調整しない |
| 4 | キャンセル・返品可能状態を明示 | DB状態値だけから遷移は決められず、許可遷移表は人間判断事項として分離 |
| 5 | 会員変更時はクーポン解除 | セッション内コードを解除し、別会員は再適用 |
| 6 | カート変更後は保持・確認時再検証 | 商品追加・削除・数量変更後も保持し、注文確認GETで再検証 |

## 4. 設計間で統一した事項

- 金額式、送料判定式、注文合計式。
- セッションの状態遷移とログアウト時のセッション破棄の関係。
- 会員実績行確保は `ON CONFLICT DO NOTHING`、ロック後に一度だけ加算。
- キャンセル／返品返還は注文状態変更と同一トランザクション、ロック順序はcoupon→member usage。
- 注文確定順序のうち、ロック・会員行確保・最終検証・上限確認までを統一。注文保存・利用数更新・snapshotの相互順序は人間判断事項として分離。
- セッション上のクーポンに適用時 `member_id` を対応付け、会員変更時に解除する。
- `target_conditions` の必須キー、null・型・カテゴリ値・正整数IDの形式を整理。未知キー・存在しない商品IDの拒否は判断事項に分離。
- DBの `subtotal_amount` は割引前商品小計を維持し、割引額をsnapshot列へ別保存する。
- 注文確定テスト対象を `POST /checkout/confirm` に統一し、`/checkout/execute` は設計対象外と明記。

## 5. 実装前調査で確認した主な不一致（履歴）

- 実装前のControllerはクーポンコードを `OrderService` に渡さず、確認時再検証もなかった。
- 実装前のSQLにはcoupon/usageテーブル、order snapshot列、`returned` 制約がなかった。
- 実装前のMapper XMLは閉じタグ後にクーポンSQLがあり、会員返還SQLは `user_id` を参照していた。
- 実装前はヘッダー税額と明細税額が異なる集計方式だった。この税額差は今回の実装で明細別クーポン割引額を保存し、明細税額を割引配賦後に再計算するよう修正した。
- 実装前のキャンセル可能状態・返品経路は確認できず、状態遷移表は人間判断事項として残した。
- セッション保持値の会員ID照合と認証時の解除はFEAT-002の実装対象として追加した。
