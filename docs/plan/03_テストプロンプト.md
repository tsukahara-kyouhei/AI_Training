# 03_テストプロンプト

## 目的
01で定義した期待結果と02の実装を照合し、変更箇所・関連回帰・全体テストを区別して検証する。失敗時は原因を分類し、仕様の範囲内で修正した場合は関連テストを再実行する。

## コピペ用プロンプト

```text
以下の共通ルールと指示に従ってテストしてください。

【共通ルール】
- AI_CODING_RULES.md（実際のファイル名に合わせる）

【今回の対象】
- 機能ID：[対象機能のIDを記載。未採番の場合は「なし」]
- 機能名：[対象の機能名を記載]
- 要件・設計書：[対象となる要件定義書・設計書のファイルパスを記載。なければ「なし」]
- 01調査・テスト計画：[01の調査結果・テスト計画のファイルパスまたは内容を記載]
- 02実装結果：[02の実装結果・変更ファイル一覧のファイルパスまたは内容を記載]
- 補足：[テスト時の制約や補足事項を記載。なければ「なし」]

【テスト開始前】
1. 01のテスト計画・期待結果と02の変更差分を確認する。
2. 現在のソース・テストコードが報告内容と一致しているか確認する。
3. テスト環境、DB接続先、対象スキーマ、テストデータ、実行コマンドを確認する。
4. 通常利用データを破壊する可能性があるテストは、許可された隔離環境でのみ実行する。
5. 期待結果が仕様・設計から確定できないケースは推測せず、未解決事項に分類する。

【テスト手順】
1. 既存テストを調査し、既に検証できている内容と不足を分ける。
2. 必要なテストだけ追加・修正する。既存テストを削除・無効化して通過させない。
3. 変更箇所のテストを実行する。
4. 変更の影響範囲に応じて関連回帰テストを実行する。
5. 01の計画またはリスクに照らして全体テストが必要な場合は実行する。実行しない場合は理由と残るリスクを記載する。
6. 各テストについて入力・前提・期待結果・実結果・根拠を記録する。
7. FAILの場合は、実装不具合、テスト不備、仕様不明、環境問題、データ不備に分類する。
8. 仕様の範囲内で修正可能な実装不具合のみ、必要最小限で修正してよい。
9. 修正した場合は、影響範囲を追跡し、失敗テストと関連回帰テストを再実行する。
10. 実行したコマンド、終了コード、テスト件数・成功・失敗・スキップ数などの証拠を記録する。

【安全・品質ルール】
- 実行していないテストをPASSとしない。
- テスト削除・無効化でPASSにしない。
- 失敗や警告を隠さない。
- DB接続先・スキーマを実行前に確認する。
- Git add / commit / pushは明示的な依頼がない限り実行しない。
- 仕様判断が必要な修正を勝手に行わない。
- 既存の作業差分を上書き・破棄しない。

【結果区分】
PASS / FAIL / NOT RUN / NOT APPLICABLE / BLOCKED
```
