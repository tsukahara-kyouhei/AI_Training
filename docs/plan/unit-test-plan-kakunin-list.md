## Q-1: SQL テスト用 DB 環境の選択

### 背景・課題

本プロジェクトは PostgreSQL 固有の機能（`JSONB`・`ILIKE`・カスタム型等）を
MyBatis マッパー XML で使用している。SQL のテストを行うには、
本番と同一の RDBMS を使う方法と、H2 などのインメモリ DB を使う方法がある。

### 方針案

#### 案 A: Testcontainers（PostgreSQL コンテナ）

JUnit 5 の `@Testcontainers` + `@Container` で Docker 上の PostgreSQL を自動起動する。

```java
@Testcontainers
@MybatisTest
@AutoConfigureTestDatabase(replace = AutoConfigureTestDatabase.Replace.NONE)
class ProductMapperTest {
    @Container
    static PostgreSQLContainer<?> postgres =
        new PostgreSQLContainer<>("postgres:16")
            .withInitScript("sql/init/init.sql");
    ...
}
```

| 観点 | 評価 |
|------|------|
| **メリット** | 本番と完全に同一の DB エンジンで検証できる |
| | PostgreSQL 固有の構文・型（JSONB、ILIKE、generate_series 等）がそのまま動作する |
| | スキーマ差異によるテスト漏れを防止できる |
| | CI 環境（GitHub Actions 等）でも Docker があれば動作する |
| **デメリット** | Docker のインストールが必要（ローカル開発・CI 共に） |
| | コンテナ起動に数秒〜十数秒かかり、テスト実行が遅くなる |
| | pom.xml に `testcontainers` 依存を追加する必要がある |

---

#### 案 B: H2 インメモリ DB（PostgreSQL 互換モード）

H2 の `MODE=PostgreSQL` を使用して擬似的に PostgreSQL として動作させる。

```yaml
# application-test.yml
spring:
  datasource:
    url: jdbc:h2:mem:testdb;MODE=PostgreSQL;DATABASE_TO_LOWER=TRUE
```

| 観点 | 評価 |
|------|------|
| **メリット** | 依存追加不要（spring-boot-starter-test に含まれる） |
| | コンテナ起動なしで高速に動作する |
| | Docker 不要でどの環境でも同様に動作する |
| **デメリット** | `JSONB`型、`ILIKE` など PostgreSQL 固有の機能の一部が非対応 |
| | H2 の差異に合わせて SQL を書き換える等の工夫が必要になる場合がある |
| | 本番 DB との差違を完全には再現できず、テストすり抜けのリスクがある |

---

#### 案 C: 専用テスト用 PostgreSQL サーバー（常設）

開発環境に常設の PostgreSQL インスタンスを構築し、テスト実行時に接続する。

| 観点 | 評価 |
|------|------|
| **メリット** | 本番と完全に同一の DB エンジン。コンテナ起動コストなし |
| | 既存の Docker Compose 環境を転用できる可能性がある |
| **デメリット** | テストが外部 DB サーバーに依存するため、CI 環境の構築コストが増える |
| | テスト間のデータ汚染リスクがあり、クリーンアップ設計が複雑になる |
| | チームメンバー全員が同一の接続設定を手動で管理する必要がある |

---

### 本プロジェクトにおける推奨方針

**→ 案 A（Testcontainers）を推奨する**

**理由**:
1. `ProductMapper.xml` には `JSONB`（`payment_instruction` 列）への参照や `ILIKE` による
   大文字小文字を無視した検索など、PostgreSQL 固有の機能が含まれている。  
   H2（案 B）ではこれらを正しくテストできず、重大なバグを見逃すリスクがある。
2. 既に `docker-compose.yml` がプロジェクトに含まれており、Docker インフラが整備済みである。
   Testcontainers の導入コストは低い。
3. CI 環境（将来的にも）で安定して動作させるためには、外部常設 DB への依存（案 C）よりも
   テスト自己完結型の Testcontainers が適している。
4. テスト実行の遅延は、`@Testcontainers` の `@Container static`
   フィールドを使ったコンテナ共有（クラス全体で 1 回起動）で最小化できる。

## Q-2: フロントエンド JS テストの導入要否

### 背景・課題

本プロジェクトは Vanilla JS で実装されており、現時点でフロント JS のテスト環境が存在しない。
Jest や Vitest を新たに導入するか、もしくはフロント JS のテストを今回のスコープから除外するかを決定する必要がある。

### 方針案

#### 案 A: Jest + jsdom を導入してテストを実装する

ルートディレクトリに `package.json` を作成し、Jest をテストランナーとして導入する。

| 観点 | 評価 |
|------|------|
| **メリット** | `submit-guard.js`（二重送信防止）や `product-detail.js`（バリアント選択）など  ビジネスロジックと密接なモジュールをファスト・フィードバックで検証できる |
| | フロント JS のリファクタリング時の安全網となる |
| | JS に `window` / `document` 依存がある場合も jsdom で対応できる |
| **デメリット** | `package.json` / `node_modules` の管理が増える（Maven プロジェクトに Node 環境が追加される）|
| | 現在の JS が ESM モジュール形式な場合、Jest での ESM 対応に設定が必要 |
| | 導入・初期設定のコストが存在する |

---

#### 案 B: フロント JS テストを今回のスコープから除外する

Java（バックエンド）のテストに集中し、フロント JS は手動テストまたは将来の E2E テストで担保する。

| 観点 | 評価 |
|------|------|
| **メリット** | ツール導入コストがなく、すぐにバックエンドテスト実装に集中できる |
| | Maven 以外の依存が増えない |
| **デメリット** | `submit-guard.js` や `product-detail.js` などのロジックが自動テストで保護されない |
| | フロント JS のバグ検出が手動テストまたは E2E テスト頼みになる |
| | JS コードが増えるにつれてリリース品質リスクが高まる |

---

#### 案 C: Vitest を導入する（Jest の代替）

Vitest は ESM ネイティブ対応で設定が簡単。ただし Node.js + 設定ファイル管理は Jest と同様に必要。

| 観点 | 評価 |
|------|------|
| **メリット** | ESM モジュールをそのまま扱えるため、設定コストが Jest より低い |
| | `vite.config.js` 一元管理で完結する |
| **デメリット** | Vite ビルドツールを使っていない本プロジェクトでは恩恵が限定的 |
| | Jest に比べてコミュニティ・ドキュメントが少ない |

---

### 本プロジェクトにおける推奨方針

**→ 案 A（Jest 導入）を推奨する**

**理由**:
1. `submit-guard.js`（二重送信防止）や `product-detail.js`（バリアント切替・在庫判定）は
   ユーザー体験に直結するロジックを含んでいる。自動テストで保護する価値が高い。
2. 本プロジェクトは Vanilla JS（ESM 形式）であり、Jest の `--experimental-vm-modules`
   または `babel-jest`（CommonJS 変換）で対応可能で、設定コストは許容範囲内。
3. まずは優先度「高」の 3 モジュール（`submit-guard` / `product-detail` / `recently-viewed`）
   のみに絞ってスモールスタートし、以後インクリメンタルに拡充することでリスクを抑えられる。

## Q-3: コードカバレッジ目標値の決定

### 背景・課題

JaCoCo によるカバレッジ計測を行う場合、目標値の設定が必要である。
高すぎると実装コストが膨らみ、低すぎると品質保証の意義が薄れる。
プロジェクトの品質要件・工数制約に応じた目標値の確認が必要。

### 方針案

#### 案 A: ライン カバレッジ 80 % 以上（stringent）

| 観点 | 評価 |
|------|------|
| **メリット** | 多くの分岐を網羅できる。バグ検出率が高い |
| | 金融・決済などの重要機能（`OrderService`）には適切な水準 |
| **デメリット** | 残り 20 % のカバレッジ向上に労力がかかる傾向がある |
| | テスト記述のための実装コストが増加する |

---

#### 案 B: ライン カバレッジ 70 % 以上（standard）

| 観点 | 評価 |
|------|------|
| **メリット** | 一般的な Web アプリの基準として適切。現実的な実装コスト |
| | ビジネスロジック中心に重点テストしつつ、補助的なコードを除外しやすい |
| **デメリット** | 30 % の未カバー部分にバグが潜む可能性が残る |

---

#### 案 C: パッケージ別に目標値を分ける（tiered）

重要度の違いを目標値に反映させる。

| パッケージ | 目標値 |
|-----------|-------|
| `service.*` | 80 % 以上 |
| `web.*` (Controller) | 70 % 以上 |
| `repository.*` | 70 % 以上 |
| `common.*` (ユーティリティ) | 90 % 以上 |
| `config.*` / `logging.*` | 除外 |

| 観点 | 評価 |
|------|------|
| **メリット** | 重要なビジネスロジックに集中しつつ、設定/ロギング等を除外できる |
| | 工数対効果が最も高い |
| **デメリット** | JaCoCo の設定が案 A/B より複雑になる |

---

### 本プロジェクトにおける推奨方針

**→ 案 C（パッケージ別目標値）を推奨する**

**理由**:
1. `OrderService`・`MemberService` など決済・個人情報を扱うビジネスロジックは 80 % 以上で
   厳しく検証しつつ、`config/` や `logging/` のような Spring Boot 設定クラスは
   テストの対象から除外することで、工数を重要箇所に集中できる。
2. `common/` のユーティリティクラス（`MoneyFormatter`・`SearchKeywordNormalizer` 等）は
   副作用がなく純粋なロジックのため 90 % 以上を達成しやすく、カバレッジ全体を底上げできる。
3. 将来的には CI で JaCoCo の `check` ゴールを設定してゲートとして機能させることが推奨される。

## Q-4: Controller テストの粒度（@WebMvcTest vs @SpringBootTest）

### 背景・課題

Spring Boot の Controller テストには `@WebMvcTest`（部分コンテキスト）と
`@SpringBootTest`（フルコンテキスト）の 2 つのアプローチが存在する。
本プロジェクトでどちらを採用するかを確認する。

### 方針案

#### 案 A: @WebMvcTest（スライステスト）を採用する

| 観点 | 評価 |
|------|------|
| **メリット** | Spring MVC 層のみロードするため起動が高速 |
| | `@MockBean` で Service をモック化することで、Controller だけに集中できる |
| | テストの独立性が高く、依存クラスの変更に強い |
| **デメリット** | Security 設定の読み込みに細かい設定が必要（`@Import(SecurityConfig.class)` 等） |
| | `@Component` が不足して起動失敗するケースがある |

---

#### 案 B: @SpringBootTest（フルコンテキスト）を採用する

| 観点 | 評価 |
|------|------|
| **メリット** | 全 Bean を起動するため設定ミスで詰まりにくい |
| | 結合に近い振る舞いを検証できる |
| **デメリット** | 全 Bean のロードが必要なため起動が遅く、テスト実行コストが高い |
| | 依存サービスの影響を受けるため、テスト対象の分離が不明確になりがち |
| | 単体テストとしての意義が薄れる |

---

### 本プロジェクトにおける推奨方針

**→ 案 A（@WebMvcTest）を推奨する**

**理由**:
1. Controller 層の単体テストとしての目的は「HTTP リクエスト/レスポンスの制御」と
   「バリデーション・認可が正しく機能すること」にあり、Service 層の動作は不要。
2. `@SpringBootTest` では外部依存（DB・メールサーバー）の設定も必要になり、
   単体テストの実行環境構築コストが増大する。
3. `SecurityConfig` の読み込み問題は `@WebMvcTest` の `excludeAutoConfiguration` または
   `@Import` で解決可能であり、設定の複雑さは許容範囲内。

## Q-5: テストデータ（フィクスチャ）の管理方法

### 背景・課題

Mapper テスト等で必要なテストデータをどのように準備・管理するかを決定する。

### 方針案

#### 案 A: @Sql アノテーション + テスト専用 SQL ファイル

| 観点 | 評価 |
|------|------|
| **メリット** | SQL ファイルで宣言的にデータを管理でき、可読性が高い |
| | スキーマを忠実に再現した状態でテストできる |
| **デメリット** | テーブルが多い場合、SQL ファイルの管理量が増える |
| | リファクタリング（列名変更等）でファイルの更新漏れが出る可能性がある |

---

#### 案 B: テストクラス内でオブジェクト生成（Builder / ObjectMother パターン）

| 観点 | 評価 |
|------|------|
| **メリット** | Java コードで管理するためコンパイル時にチェックが入る |
| | 柔軟に値を変えられる |
| **デメリット** | Mapper テストでは結局 DB に INSERT が必要なため SQL ファイルと併用が必要 |

---

#### 案 C: DBUnit / Flyway テスト拡張を使用する

| 観点 | 評価 |
|------|------|
| **メリット** | より高度なデータセット管理ができる |
| **デメリット** | 追加ライブラリの学習コストが高い。本プロジェクトの規模には過剰 |

---

### 本プロジェクトにおける推奨方針

**→ 案 A（@Sql アノテーション）を推奨する**

**理由**:
1. 現時点で `sql/seed/` に既存シードファイルがあり、テスト専用版に派生しやすい。
2. `@Sql` は Spring Test の標準機能でライブラリ追加不要。シンプルで習得コストが低い。
3. Mapper テストではどちらにしても SQL での INSERT が必要なため、
   Java のオブジェクト生成のみでは完結しない。

## Q-6: Spring Security のテスト方法

### 背景・課題

`/mypage/**` は認証必須、その他の URL は全公開という設定が `SecurityConfig` に存在する。
Controller テストで認証状態をどのようにシミュレートするかを確認する。

### 方針案

#### 案 A: @WithMockUser / @WithUserDetails を使用する

| 観点 | 評価 |
|------|------|
| **メリット** | Spring Security Test の標準機能で設定が容易 |
| | `@WithMockUser(username = "test@example.com", roles = "USER")` のように宣言的に使える |
| **デメリット** | `UserDetails` の独自フィールド（`MemberSessionUser`）を含む場合、`@WithUserDetails` でのカスタムが必要 |

---

#### 案 B: カスタム @WithMockMember アノテーションを作成する

`SecurityMockMvcRequestPostProcessors.user()` を使って本プロジェクト固有の
`MemberPrincipal` / `MemberSessionUser` をセットするカスタムアノテーションを用意する。

| 観点 | 評価 |
|------|------|
| **メリット** | テストコードが実際の認証情報と一致し、現実的なシナリオをテストできる |
| | テスト全体で再利用できる |
| **デメリット** | 初回の実装コストが発生する |

---

### 本プロジェクトにおける推奨方針

**→ 段階的に案 A から案 B へ移行することを推奨する**

**理由**:
1. まず `@WithMockUser` でシンプルに認証チェックを実装し、動作を確認する。
2. `MyPageController` など `MemberSessionUser` の独自フィールドを参照するケースでは、
   `@WithUserDetails` または `SecurityMockMvcRequestPostProcessors.user()` によるカスタム実装に移行する。
3. 共通アノテーション（`@WithMockMember`）はテストヘルパーとして `src/test/java/` に用意し、
   全テストクラスで再利用すると管理コストを削減できる。

## Q-7: Spring Batch ジョブのテスト範囲

### 背景・課題

バッチジョブ（売れ筋ランキング集計・レコメンド集計）を単体テスト計画に含めるかどうかを確認する。

### 方針案

#### 案 A: バッチジョブを単体テスト範囲に含める

| 観点 | 評価 |
|------|------|
| **メリット** | ランキング集計ロジックのバグを早期に検出できる |
| | Spring Batch の `JobLauncherTestUtils` を使えばジョブ単体のテストが可能 |
| **デメリット** | バッチジョブのテストには DB スキーマ（`spring-batch-metadata`）の準備も必要で、設定コストが高い |

---

#### 案 B: バッチジョブを単体テスト範囲から除外し、別途計画する

| 観点 | 評価 |
|------|------|
| **メリット** | 単体テストを通常の Web 機能に集中させ、実装コストを下げられる |
| **デメリット** | バッチのバグ検出が遅れる可能性がある |

---

### 本プロジェクトにおける推奨方針

**→ 案 B（今回スコープ外）を推奨する**

**理由**:
1. バッチジョブは `batch.job.enabled: false` で通常起動時に実行されないよう管理されており、
   Web 機能とは独立している。
2. バッチ固有のテスト設定（Spring Batch メタデータスキーマ・`JobLauncherTestUtils`）は

## Q-8: メールサービスのテスト方法

### 背景・課題

`NotificationMailService` は `JavaMailSender` を使ってメールを送信する。
テスト中に実際のメール送信を行わずにテストする方法を確認する。

### 方針案

#### 案 A: JavaMailSender を @MockBean でモックする

| 観点 | 評価 |
|------|------|
| **メリット** | Spring Test 標準のモック機能で実装が容易 |
| | `verify(mailSender).send(any(MimeMessage.class))` でメール送信確認が可能 |
| **デメリット** | メール内容（件名・本文）の詳細検証が難しい |

---

#### 案 B: MailTemplateRenderer を個別に単体テストし、送信は別途検証

`NotificationMailService` の送信部はモック、`MailTemplateRenderer` のテンプレート描画は
別の単体テストクラスで実際の描画結果を検証する。

| 観点 | 評価 |
|------|------|
| **メリット** | テンプレートの正確な本文・件名を文字列レベルで検証できる |
| | 責務ごとに独立したテストができる |
| **デメリット** | テストクラスが 2 つに分かれる |

---

### 本プロジェクトにおける推奨方針

**→ 案 B（責務分離テスト）を推奨する**

**理由**:
1. `MailTemplateRenderer` のテンプレート描画ロジック（件名・本文の生成）は
   純粋な文字列変換であり、独立した単体テストで詳細に検証すべきである。
2. `NotificationMailService` の「送信が呼ばれたこと」の検証は
   `@MockBean JavaMailSender` + `verify()` で十分であり、責務を分離することで
   テストの可読性と保守性が向上する。

## Q-9: トランザクション管理（テスト後クリーンアップ）方式

### 背景・課題

Mapper テストでデータを INSERT した場合、テスト後にデータをどのようにクリーンアップするかを確認する。

### 方針案

#### 案 A: @Transactional によるロールバックを使用する

テストクラスに `@Transactional` を付与し、テスト完了後に自動ロールバックする。

| 観点 | 評価 |
|------|------|
| **メリット** | 設定が簡単でコード量が少ない |
| | 各テスト後に確実にデータが元の状態に戻る |
| **デメリット** | `REQUIRES_NEW` でトランザクションを分割する処理（採番ロジック等）は検証が難しい場合がある |
| | ロールバックにより副作用の確認ができないケースがある |

---

#### 案 B: @Sql(executionPhase = AFTER_TEST_METHOD) でクリーンアップ SQL を実行する

| 観点 | 評価 |
|------|------|
| **メリット** | `REQUIRES_NEW` を使う採番処理など、トランザクション境界をまたぐテストに対応できる |
| **デメリット** | クリーンアップ SQL の管理が必要。DELETE 漏れのリスクがある |

---

### 本プロジェクトにおける推奨方針

**→ 案 A（@Transactional ロールバック）を基本とし、採番テスト等は例外的に案 B を使用する**

**理由**:
1. 大半のテストケースは `@Transactional` で十分なクリーンアップが可能であり、
   管理コストが最も低い。
2. `order_number_counters` の採番ロジック（`REQUIRES_NEW` を内部で使う可能性がある）など、
   ロールバックで正しく検証できない特殊ケースのみ `@Sql(AFTER_TEST_METHOD)` を使う。

### 解答欄

| 項目 | 内容 |
|------|------|
| 決定方針 | 案 A 基本 + 例外案 B |
| 例外ケースの有無 | 採番ロジックに REQUIRES_NEW あり → 案 B 併用 |

## Q-10: CartCookieStore のテスト方針

### 背景・課題

`CartCookieStore` はカートデータを DB ではなく HTTP クッキーに保存する特殊な実装である。
`HttpServletRequest` / `HttpServletResponse` に直接依存しているため、
テスト方法の確認が必要。

### 方針案

#### 案 A: MockHttpServletRequest / MockHttpServletResponse を使用する

Spring Test に含まれる `MockHttpServletRequest` / `MockHttpServletResponse` を使って
クッキーを模擬する。

| 観点 | 評価 |
|------|------|
| **メリット** | 追加ライブラリ不要。Spring Test に同梱されている |
| | クッキーの設定・読み取りを精密に検証できる |
| **デメリット** | モック生成のボイラープレートコードがやや多め |

---

#### 案 B: @WebMvcTest の MockMvc 経由で間接的にテストする

Controller テストの中でカート操作リクエストを送信し、クッキーがセットされることを検証する。

| 観点 | 評価 |
|------|------|
| **メリット** | E2E に近い形で CartCookieStore を含む一連の動作が検証できる |
| **デメリット** | Controller のテストと CartCookieStore のテストが混在し、失敗時の原因特定が困難になる |

---

### 本プロジェクトにおける推奨方針

**→ 案 A（MockHttpServletRequest/Response）を推奨する**

**理由**:
1. `CartCookieStore` はクッキーのシリアライズ/デシリアライズ・有効期限設定など
   独自の責務を持つため、Controller とは分離して単体で検証すべきである。
2. `MockHttpServletRequest` / `MockHttpServletResponse` は Spring Test に含まれており、
   追加依存なしに利用できる。ボイラープレートはヘルパーメソッドで解消できる。
