# 単体テスト計画書

## 1. 目的
本プロジェクトにおける単体テストの方針を整理し、Controller と Service の主要な業務ロジックについて、品質と保守性を高めるための実施基準を定義する。

## 2. テスト対象
### 2.1 対象
- Controller
  - 認証系
  - 商品系
  - カート・購入フロー系
  - 会員登録・マイページ系
  - お問い合わせ系
- Service
  - 会員登録・認証・プロフィール管理
  - 商品検索・商品詳細取得
  - カート操作
  - 注文処理
  - お問い合わせ処理

### 2.2 対象外
- Repository
- SQL（schema）
- データベース
- Thymeleaf テンプレート
- CSS
- JavaScript
- 外部サービス連携（メール送信など）

## 3. テスト方針
### 3.1 テストフレームワーク
- Controller テスト: `@WebMvcTest`
- Service テスト: `@ExtendWith(MockitoExtension.class)`
- モックライブラリ: Mockito

### 3.2 テスト観点
- 正常系
- 代表的な異常系
  - 入力チェック
  - バリデーションエラー
  - データ未存在
  - 権限不足
  - 想定される例外

### 3.3 テスト粒度
- 重要な業務ロジックを優先し、条件分岐・例外分岐・画面遷移・モデル属性の設定を重点的にテストする。
- コードカバレッジは 80% 以上を目標とするが、数値目標だけでなく、業務価値の高い箇所を優先してテストを実施する。

## 5. テストケース設計方針
### 5.1 Controller テスト
Controller テストでは、以下を確認する。

- 適切な View 名を返すこと
- 適切なモデル属性が設定されること
- リダイレクト先が正しいこと
- バリデーションエラー時に入力画面へ戻ること
- 未ログイン・未認可・対象データ未存在時に適切な遷移または例外が発生すること

### 5.2 Service テスト
Service テストでは、以下を確認する。

- 正常な入力で期待値が返却されること
- 例外が発生する条件で、想定した例外が送出されること
- リポジトリ呼び出しが適切に行われること
- 条件分岐により別の結果が返ること

## 6. テストデータ方針
- 各テストメソッド内で必要なデータを作成する。
- テスト間でデータを共有しない。
- 可能な限り、テスト対象の入力・出力に集中した最小構成のデータを使用する。
- 外部依存がある処理は、Mockito でスタブ化する。

## 7. 命名規則
### 7.1 テストクラス
- 形式: `対象クラス名 + Test`
- 例: `CartControllerTest`, `MemberServiceTest`

### 7.2 テストメソッド
- 形式: `対象メソッド_テスト区分_条件`
- 例:
  - `login_正常系_未ログインでログイン画面を表示する`
  - `updateProfile_異常系_バリデーションエラーの場合は入力画面へ戻る`
  - `placeOrder_異常系_カートが空の場合は例外を返す`

## 8. テスト実施タイミング
- 実装完了後
- 修正後（影響範囲の単体テストを再実施）
- プルリクエスト・レビュー前

## 9. 優先度
### 9.1 優先度高
- 会員登録・ログイン
- 商品検索・商品詳細表示
- カート追加・更新・削除
- 注文確定処理
- お問い合わせ送信
- 会員情報変更・追加お届け先管理
- お気に入り追加・解除

### 9.2 優先度中
- お知らせ表示
- 購入履歴表示
- 退会処理

## 10. テストケース例
### 10.1 Controller
- `login_正常系_未ログインでログイン画面を表示する`
- `login_異常系_既にログイン済みならマイページへリダイレクトする`
- `checkoutInputSubmit_異常系_バリデーションエラー時は入力画面を返す`
- `toggleFavorite_異常系_未ログインならログイン画面へ遷移する`
- `memberRegister_confirm_異常系_重複メールアドレスなら入力画面へ戻る`

### 10.2 Service
- `register_正常系_会員を登録できる`
- `register_異常系_重複メールアドレスなら例外を送出する`
- `updateProfile_異常系_バリデーション不備なら更新しない`
- `toggleFavorite_正常系_未登録のお気に入りを追加できる`
- `toggleFavorite_異常系_登録済みのお気に入りは解除される`
- `placeOrder_正常系_注文ヘッダ・明細・履歴を登録できる`
- `placeOrder_異常系_カートが空なら例外を送出する`
- `findDetail_異常系_商品が存在しない場合は空を返す`

## 11. テスト実施手順
1. 対象クラスに対してテストクラスを作成する。
2. モック依存を `Mockito` で注入する。
3. 正常系・異常系ごとにテストメソッドを作成する。
4. 実行結果を確認し、必要に応じて追加テストを実施する。
5. 重要な業務ロジックに関しては、条件分岐ごとにテストを補完する。

## 12. 実装・保守上の注意
- テストコードは可読性を重視し、検証意図が明確になるように命名する。
- 実装詳細ではなく、振る舞いに着目してテストする。
- テスト対象が変更された場合は、関連する単体テストも併せて更新する。
- 外部サービス連携や DB 依存のテストは、単体テストの対象外とする。

## 13. 期待成果
- 主要な Controller と Service の業務ロジックに対する回帰テスト基盤を整備する。
- バグの早期発見と修正容易性を向上させる。
- プルリクエスト時に、重要な機能変更の影響範囲を確認しやすくする。
