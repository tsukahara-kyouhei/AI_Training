# 単体テスト計画

## 1. 目的

本計画は、OFFICE ORDER のサービス層・リポジトリ層を中心に、業務ロジック、入力値の正規化、例外分岐、データアクセスパラメータを単体テストで検証するための方針を定める。

今回の重点は、注文・在庫・会員領域とする。既存の注文確定障害を踏まえ、正常系だけでなく、注文番号の採番、在庫不足、DB制約に関係する境界条件を優先する。

## 2. 対象範囲

### 2.1 単体テストの対象

| 対象 | テスト内容 |
|---|---|
| サービス層 | 業務ルール、入力正規化、分岐、例外、トランザクション境界に渡す処理 |
| リポジトリ層 | Mapper呼び出し、パラメータ変換、戻り値変換、Optional・空結果の扱い |
| 商品検索ロジック | キーワード、全角半角、大小文字、価格帯、在庫、カテゴリ条件、ページ補正 |
| 注文ロジック | 入力検証、在庫再確認、注文番号、金額計算、注文保存、メール予約 |
| 会員ロジック | 登録、メール重複、プロフィール変更、退会、住所、お気に入り |
| バッチロジック | ランキング・関連商品集計、順位付け、上限、全置換 |
| 共通ロジック | リダイレクト先正規化、日付・金額・入力値変換など、独立した業務ヘルパー |

### 2.2 単体テストの対象外

| 対象外 | 検証するテスト |
|---|---|
| ControllerのHTTP入出力・画面遷移 | Controllerスライステスト、MockMvcテスト |
| MyBatis XMLとPostgreSQLの実SQL実行 | Repository/SQL統合テスト |
| Thymeleafのレンダリング | 画面・ブラウザテスト |
| Spring Securityの実認証設定 | Security統合テスト |
| Docker、PostgreSQL初期化、メールサーバー接続 | 環境・結合テスト |
| Spring Batchメタデータの実書込み | Batch統合テスト |

単体テストで確認できない結合点は、別テスト計画または統合テストの課題として管理する。

## 3. テスト方式

- Java 21、JUnit 5、Spring Boot Testの標準機能、Mockitoを使用する。
- 外部依存は原則モック化し、1テストの対象クラスの判断だけを検証する。
- 時刻は `Clock` または `AppTimeProvider` を固定値に差し替える。
- DBの実制約、MyBatis XML、PostgreSQLの型変換は単体テストで代替せず、統合テストで確認する。
- テスト名は「条件・操作・期待結果」が分かる形式とする。
- テスト間で状態を共有せず、各テストで入力・モック・期待値を準備する。
- ランダム値、現在時刻、メール送信、セッション／Cookieなどの非決定要素はモックまたは固定値で制御する。

## 4. テスト観点

### 4.1 共通観点

- 正常値、空値、NULL、未指定
- 境界値（0、1、最大値、最大値超過）
- 不正値、形式不正、重複値
- 大文字・小文字、全角・半角、前後空白
- 空リスト、重複リスト、存在しないID
- Optionalの値あり／空
- Repositoryが返すNULL、0件、複数件
- 例外発生時の変換・再送出・ログ対象
- 同じ入力に対する結果の再現性

### 4.2 注文・在庫

| ID | テスト観点 | 期待結果 |
|---|---|---|
| ORD-001 | 正常な1商品注文 | 注文ヘッダ、明細、ステータス履歴の保存情報が正しい |
| ORD-002 | 複数商品注文 | 商品数分の明細とメール明細が作成される |
| ORD-003 | 空カート | 業務エラーとなり、保存処理を呼ばない |
| ORD-004 | 在庫0 | 在庫不足として拒否し、注文保存を呼ばない |
| ORD-005 | 注文数量が在庫超過 | 在庫不足として拒否し、注文保存を呼ばない |
| ORD-006 | 注文数量が在庫以内 | 注文確定処理を継続する |
| ORD-007 | 日次連番の初回 | 連番1から注文番号を生成する |
| ORD-008 | 日次連番の既存値 | 取得した連番で注文番号を生成する |
| ORD-009 | 連番上限超過 | 注文を保存せず、上限超過例外となる |
| ORD-010 | 個人注文 | 会社名なしで注文パラメータを作成できる |
| ORD-011 | 法人注文の会社名なし | 業務エラーとなる |
| ORD-012 | コンビニ決済 | 支払案内JSONを生成して保存パラメータへ設定する |
| ORD-013 | コンビニ以外の決済 | 支払案内JSONをNULLとして扱う |
| ORD-014 | 税率未取得 | 規定のデフォルト税率を使用する |
| ORD-015 | 商品別税額 | 指定の丸め規則で明細税額を計算する |
| ORD-016 | トランザクション同期なし | 注文完了メール予約の失敗として扱う |
| ORD-017 | DB保存例外 | 例外を呼び出し元へ伝播し、完了メールを送信しない |
| ORD-018 | 在庫更新仕様の確認 | 現行実装が在庫を再確認するのみで、`stock_quantity` を更新しないことを確認する。購入時の引落しを仕様化する場合は、別途統合テストと実装変更が必要 |
| ORD-019 | 注文番号重複 | 一意制約違反などDB側の例外がサービス境界を越えて伝播することを確認する |

### 4.3 会員・認証関連

| ID | テスト観点 | 期待結果 |
|---|---|---|
| MEM-001 | 有効会員の認証情報取得 | 会員情報を返す |
| MEM-002 | 未登録メール・退会会員 | 認証対象なしとして扱う |

| MEM-004 | 登録前メール重複 | 重複例外となり、登録しない |
| MEM-005 | 登録時の重複競合 | DB例外を重複例外へ変換する |
| MEM-006 | プロフィール更新 | 正常に更新し、更新後情報を再取得する |
| MEM-007 | 他会員とメール重複 | 更新を拒否する |
| MEM-008 | 会員退会 | 会員状態と退会日時の更新を依頼する |

| MEM-011 | 追加お届け先更新・削除 | 対象会員の所有範囲だけを操作する |

### 4.4 商品・検索

| ID | テスト観点 | 期待結果 |
|---|---|---|
| PRD-001 | 商品コード完全一致 | 対象商品だけを検索条件へ渡す |
| PRD-002 | 商品コード前方一致 | 区切りを考慮した前方一致パターンを生成する |
| PRD-003 | 商品名・説明・バリエーション部分一致 | 正規化済み検索条件を生成する |
| PRD-004 | 全角半角・大小文字 | NFKCと小文字化で同一条件にする |
| PRD-005 | SQLワイルドカード文字 | `%`、`_`、バックスラッシュをエスケープする |
| PRD-006 | 価格帯・カラー・在庫 | 有効な条件だけを検索条件へ反映する |
| PRD-007 | カテゴリ固有フィルタ | デスク、チェア、収納家具の条件を分離して扱う |
| PRD-008 | 不正な候補ID | 候補一覧にないIDを除外する |
| PRD-009 | ページ番号・表示件数 | 下限補正と許可サイズへの補正を行う |
| PRD-010 | 0件・ページ超過 | 空結果または最終ページへの補正を正しく扱う |

| ID | テスト観点 | 期待結果 |
|---|---|---|

| BAT-002 | 売れ筋上限 | 上位10件だけを保存対象にする |
| BAT-003 | ランキング再生成 | 対象日データを削除してから再登録する |

| BAT-006 | 自商品推薦の除外 | sourceとrecommendedが同一の商品を作成しない |
| BAT-007 | 関連商品上限 | 商品ごとに上位4件だけを保存対象にする |

### 4.6 リポジトリ・データ変換

- Mapperが返す1件、複数件、0件、NULLの変換を確認する。
- `Optional.empty()`、空リスト、デフォルト値の扱いを確認する。
- 注文・会員・商品モデルへの列変換を確認する。
- 金額、日付、JSON、NULL可能項目の変換を確認する。
- SQL実行そのものではなく、Mapperに渡すパラメータと戻り値の変換を検証する。

## 5. テストデータとモック方針

| 対象 | 方針 |
|---|---|
| 注文 | 固定時刻、固定税率、1商品・複数商品、在庫0・不足・十分を用意する |
| 会員 | 個人・法人、未登録・有効・退会、メール重複を用意する |
| 商品 | `P0001-C01`、`P0001-C02`、在庫あり・在庫なし、カテゴリ別属性を用意する |
| バッチ | 同数順位、10件超、キャンセル注文、共起なしを用意する |
| DBアクセス | Mapperをモック化し、戻り値と例外をテストごとに設定する |
| 時刻 | `Clock.fixed` 等で固定し、日付境界を再現する |
| メール | 送信サービスをモック化し、呼出条件だけを検証する |

本番・共有DBには単体テストから接続しない。seedデータに依存せず、テスト内で必要な値を明示する。

## 6. 品質基準・完了条件

- 重要分岐（注文、在庫、会員重複、認証、バッチ全置換）のテストがすべて実装されている。
- 正常系だけでなく、NULL、空、境界値、不正値、例外系を含む。
- 行カバレッジの目標は80%以上、重要サービスの分岐カバレッジの目標は70%以上とする。
- カバレッジ数値だけで合格とせず、ORD、MEM、BATの必須ケースを満たすことを優先する。
- テストはローカル環境で再実行可能で、実行順に依存しない。
- 失敗時に対象ユースケース、入力条件、期待結果が特定できるテスト名とする。
- `mvnw.cmd test` が成功することを単体テストの実行完了条件とする。

## 7. 実行方法

```powershell
.\mvnw.cmd test
```

特定クラスだけを実行する場合:

```powershell
.\mvnw.cmd -Dtest=OrderServiceTest test
```

カバレッジを計測する場合は、プロジェクトへ導入済みのカバレッジプラグインがある場合に限り、その設定に従う。未導入の場合は、まずJUnitの必須ケース消化とテスト結果を品質記録とする。

## 8. 既存テストとの関係

- `ProductKeywordSearchTest` のような検索条件の単体テストは、PRD系テストの先行実装として扱う。
- `ProductSearchIntegrationTest` はDB・Mapper・画面経路を含むため、本計画の単体テストとは区別する。
- 注文・会員・カート・バッチは、本計画の追加対象として優先的にテストを整備する。
