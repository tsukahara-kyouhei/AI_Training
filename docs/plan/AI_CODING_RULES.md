# AIコーディングルール

> **目的**：AIがソースコードの作成・修正・レビュー・テストを行う際に守るルールを定義します。
>
> -   **`【USER EDIT】`**：プロジェクトメンバーが編集する箇所。
> -   **`【AI FIXED RULE】`**：AIが守る共通ルール。通常の開発作業では変更しない。
> -   上位のシステム・開発者・ユーザーからの明示的な指示を優先する。
> -   既存実装と要件・設計書が矛盾する場合、AIが勝手に判断せず矛盾点を報告する。

------------------------------------------------------------------------

# 1. ルールの優先順位

## 【AI FIXED RULE】

次の優先順位で適用します。

1.  上位のシステム・開発者・ユーザーからの指示
2.  明示された要件・承認済みの設計
3.  本 `AI_CODING_RULES.md`
4.  既存実装・プロジェクト規約
5.  一般的なコーディング慣習

情報が矛盾する場合は、推測で決めず、矛盾点と根拠を報告します。

# 3. プロジェクト固有のコーディング規約

## 【USER EDIT】

### 3.1 命名規則

-   クラス名：責務が分かるPascalCase
-   メソッド名：処理内容が分かるcamelCase
-   変数名：用途が分かるcamelCase
-   定数名：大文字＋アンダースコア
-   テストクラス名：対象クラス・機能が分かる名前とし、既存規約に合わせる

### 3.2 API規約

-   URL命名：既存APIの命名規則に従う。既存の商品検索では`/products/search` を使用する
-   HTTPメソッド：既存API設計・実装に従う
-   リクエスト形式：既存API設計・実装に従う
-   レスポンス形式：既存API設計・実装に従う
-   エラーレスポンス：既存のエラー処理・`error_code` 等の仕様に従う
-   使用するステータスコード：既存API設計・実装に従い、勝手に変更しない

### 3.3 DB規約

-   テーブル命名：既存DBの命名規則に従う。
-   カラム命名：既存DBの命名規則に従う。
-   主キー・外部キーは既存テーブル定義に従う。
-   外部キー：既存テーブル定義に従う
-   NULLの扱い：`NULL`、空文字、空白を区別し、既存仕様に従う
-   マイグレーションルール：既存DB変更方式に従い、明示的な要件なしにスキーマを変更しない

### 3.4 テスト規約

-   必須テスト種別：変更内容に応じてJUnit 5 / Spring Boot Testを使用する。
-   テストクラス命名：テストクラス名は既存規約に合わせる。
-   必須テスト観点：正常系、異常系、境界値、NULL、空文字、不正値、既存機能への影響を確認する。
-   結合テスト方針：DB・Mapper・Service等の連携を変更する場合は、既存テスト構成を確認して必要な結合テストを実施する。

# 6. 情報の確認ルール

## 【AI FIXED RULE】

既存動作を確認するときは、原則として次の順で確認します。

1.  実際のソースコード
2.  実際のDB定義・SQL
3.  実際の設定ファイル
4.  既存の自動テスト
5.  承認済みの設計書
6.  要件定義書
7.  一般的な推測

**既存実装がそのまま最終仕様とは限りません。**

-   要件・設計書：これから実現したい仕様
-   ソースコード・DB・テスト：現在実際に動いている仕様

機能追加などで既存動作を変更する場合は、要件・承認済み設計に従います。

------------------------------------------------------------------------

# 7. 実装前の調査ルール

## 【AI FIXED RULE】

変更前に、変更内容に応じて以下を確認します。

-   Controller
-   Service
-   Repository / Mapper
-   Entity / DTO / Model
-   SQL
-   DBテーブル・カラム定義
-   既存テスト
-   設定ファイル
-   API仕様
-   画面・テンプレート
-   例外処理
-   トランザクション処理

**1つのファイルだけ確認して、すぐに実装を開始してはいけません。**

# 8. 推測禁止

## 【AI FIXED RULE】

次の情報を推測で作ってはいけません。

-   クラス名・メソッド名
-   テーブル名・カラム名
-   API URL・リクエスト・レスポンス
-   エラーコード
-   既存動作
-   外部API
-   設定値
-   ライブラリバージョン

見つからない場合は、プロジェクト内を検索し、それでも確認できなければ「確認できなかった情報」として報告します。

# 9. 実装手順

## 【AI FIXED RULE】

① 依頼内容を理解
② 対象機能を特定
③ 既存ソースを調査
④ 要件・設計・DB・テストを確認
⑤ 現在の動作と要求との差分を確認
⑥ 必要最小限の変更範囲を決定
⑦ 実装
⑧ コードレビュー
⑨ テスト実行
⑩ 結果を報告

# 10. 必要最小限の変更

## 【AI FIXED RULE】

変更は依頼された内容に必要な範囲に限定します。

以下は禁止します。

-   無関係なリファクタリング
-   無関係なクラス名変更
-   無関係なフォーマット変更
-   無関係なSQL変更
-   無関係なライブラリ更新
-   無関係な画面変更
-   無関係な仕様変更
-   「きれいにする」という理由だけの変更

------------------------------------------------------------------------

# 11. Javaコーディングルール

## 【AI FIXED RULE】

既存プロジェクトの記述方法を優先します。

-   分かりやすい名前を使用する。
-   1つのメソッドに複数の責務を詰め込みすぎない。
-   不要なネストを増やさない。
-   同じビジネスロジックを重複させない。
-   適切な場合はマジックナンバー・文字列を定数化する。
-   例外を握りつぶさない。
-   `System.out.println` をアプリケーションログに使用しない。
-   不要なUtilityクラスを増やさない。
-   既存コードで解決できる場合は新しいライブラリを追加しない。

------------------------------------------------------------------------

# 12. Controllerのルール

## 【AI FIXED RULE】

Controllerは主に以下を担当します。

-   リクエストの受け取り
-   パラメータ確認
-   入力値の基本的な検証
-   認証・認可との連携
-   Serviceの呼び出し
-   レスポンス生成

大きなビジネスロジックやServiceのビジネスルールを重複して記述しません。

------------------------------------------------------------------------

# 13. Serviceのルール

## 【AI FIXED RULE】

Serviceはビジネスルール・アプリケーション処理を担当します。

例：クーポン適用条件、注文処理、商品検索条件、ステータス変更、金額計算。

Controllerを短くする目的だけでビジネスロジックをControllerへ移動しません。

------------------------------------------------------------------------

# 14. Repository / Mapperのルール

## 【AI FIXED RULE】

Repository / Mapperは主にデータアクセスを担当します。

-   SQLを読みやすくする。
-   条件を明確にする。
-   SQLの意味を意図せず変更しない。
-   ページング時は件数取得SQLと一覧取得SQLの条件を一致させる。
-   パラメータバインドが利用できる場合、危険な文字列連結を使用しない。

------------------------------------------------------------------------

# 15. SQLルール

## 【AI FIXED RULE】

SQL変更時は以下を確認します。

1.  テーブル名
2.  カラム名
3.  データ型
4.  NULLの扱い
5.  JOINによる重複
6.  WHERE
7.  ORDER BY
8.  ページング
9.  必要な場合のインデックスへの影響
10. `LIKE` / `ILIKE` の特殊文字

DB製品による挙動差を考慮し、PostgreSQL固有仕様は実際の環境に合わせます。

------------------------------------------------------------------------

# 16. NULL・空文字・空白の扱い

## 【AI FIXED RULE】

以下を別の値として扱います。

-   `NULL`
-   空文字 `''`
-   空白だけの文字列
-   `0`
-   空のコレクション

仕様上の理由なく同一扱いにしません。

------------------------------------------------------------------------

# 17. 例外処理

## 【AI FIXED RULE】

以下は禁止します。

-   理由なく `Exception` を広く捕捉する。
-   例外を握りつぶす。
-   失敗した処理を成功として返す。
-   原因調査に必要な情報を理由なく削除する。

追加時は既存プロジェクトの例外処理方式に従います。

------------------------------------------------------------------------

# 18. ログ

## 【AI FIXED RULE】

既存のログフレームワークとログレベルを使用します。

以下をログ出力しません。

-   パスワード
-   認証トークン
-   APIキー
-   シークレット
-   不要な個人情報
-   機密情報

------------------------------------------------------------------------

# 19. トランザクション

## 【AI FIXED RULE】

追加・変更時は以下を確認します。

1.  現在のトランザクション境界
2.  Service / Repositoryの呼び出し順
3.  同時に成功・失敗させる必要があるDB処理
4.  既存のトランザクション設定

DB処理が複数あるだけで新しいトランザクション境界を追加しません。

明確な要件やインフラ上の根拠がない状態で、分散トランザクションや2フェーズトランザクションを追加しません。

------------------------------------------------------------------------

# 20. ライブラリ・設定変更

## 【AI FIXED RULE】

不要なライブラリ追加・削除・バージョンアップを行いません。

変更が必要な場合は、必要性、影響ファイル、Java / Spring
Boot等との互換性、ビルド結果、テスト結果を確認します。

ソースコードにパスワードや秘密情報を直接記述しません。

------------------------------------------------------------------------

# 21. テストルール

## 【AI FIXED RULE】

変更内容に応じて必要なテストを確認します。

基本観点：

-   正常系
-   異常系
-   境界値
-   NULL
-   空文字
-   空白
-   不正値
-   権限
-   認証
-   既存機能への影響
-   回帰
-   DB動作
-   API動作
-   トランザクション

検索・絞り込みでは必要に応じて、完全一致、前方一致、部分一致、大文字・小文字、全角・半角、前後空白、`%`
`_` `\`、0件、ページング、ソートを確認します。

------------------------------------------------------------------------

# 22. テスト結果の報告

## 【AI FIXED RULE】

**実際に実行していないテストを「成功」と報告してはいけません。**

  結果               意味
  ------------------ ----------------------------------
  `PASS`             実行して成功
  `FAIL`             実行して失敗
  `NOT RUN`          実行していない
  `NOT APPLICABLE`   今回の変更には該当しない
  `BLOCKED`          環境・設定等の問題で実行できない

例：

```
単体テスト：PASS
結合テスト：NOT RUN
全体ビルド：PASS
```

------------------------------------------------------------------------

# 23. 実装完了前のコードレビュー

## 【AI FIXED RULE】

### 正しさ

-   依頼内容を満たしているか。
-   要件・設計に合っているか。
-   既存動作が維持されているか。
-   境界値・異常系に問題がないか。

### 変更範囲

-   依頼された範囲内か。
-   無関係なファイルを変更していないか。

### 保守性

-   処理内容を理解できるか。
-   同じ処理が重複していないか。
-   メソッドの責務が明確か。

### セキュリティ

-   秘密情報が漏れていないか。
-   入力値を安全に扱っているか。
-   SQLインジェクションの危険がないか。
-   機密情報をログ出力していないか。

### テスト

-   必要なテストを追加・更新したか。
-   実行可能なテストを実行したか。
-   結果を正確に報告しているか。

------------------------------------------------------------------------

# 24. AIの回答における情報の区分

## 【AI FIXED RULE】

-   **確認済み**：ソースコード、設定、テスト、DB定義等から確認できた情報。
-   **要件**：ユーザーまたは承認済み要件に明記された内容。
-   **設計判断**：承認済み設計として決定された内容。
-   **推奨**：必須ではない改善案。
-   **未確認**：プロジェクト内の情報から確認できなかった内容。

推奨事項を既存仕様として報告せず、推測を確認済みとして報告しません。

------------------------------------------------------------------------

# 25. 曖昧な依頼への対応

## 【AI FIXED RULE】

仕様変更につながらない曖昧さは既存プロジェクトのルールに従います。

以下が変わる場合は勝手に決定しません。

-   API
-   DB
-   ビジネスルール
-   セキュリティ
-   トランザクション
-   ユーザーから見える動作

その場合は、**何が曖昧か／現在どうなっているか／選択肢／必要な判断**を報告します。

------------------------------------------------------------------------

# 26. ドキュメント作成・修正ルール

## 【AI FIXED RULE】

ドキュメントと実装を一致させます。

-   実際のクラス名・メソッド名・テーブル名・カラム名を使用する。
-   未実装機能を「実装済み」と記載しない。
-   不要になった記述を整理する。
-   用語を統一する。
-   曖昧な表現をできるだけ使用しない。

根拠なく以下を使用しません。

`要確認` / `残課題` / `実装時` / `必要に応じて` / `検討する` / `要実装`
/ `再確認が必要` / `現時点では未確定` / `最終確認が必要`

確認できない場合は、以下のように具体化します。

```
未確認：
確認対象：
確認したファイル：
```

------------------------------------------------------------------------

# 27. AIが勝手に行ってはいけないこと

## 【AI FIXED RULE】

明示的な依頼がない限り、以下を行いません。

-   プロジェクト全体の書き換え
-   無関係なリファクタリング
-   アーキテクチャ変更
-   DBスキーマ変更
-   公開API変更
-   外部サービス追加
-   ライブラリ追加
-   テスト削除
-   バリデーション・セキュリティチェックの弱体化
-   コンパイル・テストエラーを隠す
-   失敗コードをコメントアウトして解決したことにする
-   未検証の状態で「完了」と報告する
-   Git commit / push は、ユーザーから明示的な指示がない限り実施しない。
-   `git add`、`git commit`、`git push` をユーザーの明示的な指示なしに実行してはいけない。
-   実装・テスト・最終レビューが完了しても、AIが自動的にコミットしてはいけない。
-   コミット前に変更内容・テスト結果・Git差分をユーザーが確認できる状態にする。
-   ユーザーから明示的にコミットを依頼された場合のみ、コミットを実施する

# 30. 完了条件

## 【AI FIXED RULE】

以下を満たした場合を実装完了とします。

-   依頼された機能が実装されている。
-   要件・承認済み設計と一致している。
-   維持すべき既存動作が維持されている。
-   変更コードをレビューしている。
-   必要なテストを追加・更新している。
-   実行可能なテストを実行している。
-   テスト結果を正確に報告している。
-   無関係な変更を行っていない。
-   未解決の問題があれば明確に報告している。
-   Git commit / push は実装完了条件に含めず、ユーザーの明示的な指示がある場合のみ実施する。

# 31. プロジェクト固有のAIへの指示

## 【USER EDIT】

-   実装前に `docs/` と関連する要件・設計書を確認する。
-   関連する既存ソースコードを確認する。
-   MyBatisのSQL変更時は実際のDB定義・SQLを確認する。
-   商品検索変更時はFEAT-001の要件・設計・既存検索実装を確認する。
-   クーポン・注文処理変更時はFEAT-002の要件・設計・既存注文実装を確認する。
-   Java変更後は該当するJUnit 5 / Spring Boot Testを実行する。
-   API変更時はAPI設計書とController・Serviceを照合する。
-   DB変更時はDB定義・SQL・Mapper・関連Javaコードを照合する。

-   推測を確認済みとして報告しない。
-   無関係なリファクタリングを行わない。
-   要件・設計・実装に矛盾がある場合は矛盾点を明示する。

# 34. 成果物横断の整合性確認

## 【AI FIXED RULE】

要件定義書、承認済み設計書、画面、API、DB定義、SQL / Mapper、実装コード、テストを個別に確認するだけでなく、相互の整合性を確認します。

対象機能に関係する項目について、次の対応関係を確認してください。

- 要件 → 設計
- 設計 → 画面 / API / DB
- 画面 / API / DB → 実装
- 実装 → テスト
- テスト結果 → 完了報告

必要に応じて、項目名、入力値、型、必須・任意、NULLの扱い、初期値、境界値、エラー時の動作、権限、トランザクション、データの保存・表示を照合します。

横断確認の結果は次の区分で記録します。

- `一致`：根拠を確認し、内容が一致している
- `不一致`：具体的な矛盾がある
- `未確認`：必要な根拠を確認できていない
- `対象外`：対象外である理由を説明できる

不一致・未確認には、資料名、ファイル名、クラス・メソッド・SQL・テスト名などの具体的な箇所を付けます。成果物が存在することだけをもって、整合性が取れていると判断してはいけません。

------------------------------------------------------------------------

# 35. 未解決事項の分類と質問の集約

## 【AI FIXED RULE】

未解決事項は次の3種類に分類します。

1. **AIが調査して解決する事項**：ソース、DB定義、SQL、設定、既存テスト、設計書などを調べれば解決できる事項。まず必要な調査を行います。
2. **人間の判断が必要な事項**：業務ルール、要件の優先順位、仕様変更、セキュリティ、API / DB変更、対象範囲拡大など、調査だけでは確定できない事項。
3. **今回の実装に影響しない事項**：影響しない理由と根拠を示せる事項。

AIが調査して解決できる事項を、調査せずに人間へ質問してはいけません。

人間の判断が必要な事項は、可能な範囲で一度にまとめて質問します。各質問には以下を含めます。

- 判断が必要な理由
- 根拠となる資料・実装箇所
- 選択肢
- 各選択肢の影響
- 推奨案とその根拠（確定済みの要件・事実から推奨できる場合）

判断が必要な事項を推測で決めて実装してはいけません。質問の回答待ちであっても、仕様判断に影響しない独立した調査や作業は進めて構いません。

------------------------------------------------------------------------

# 36. 証拠に基づく確認・報告

## 【AI FIXED RULE】

「確認した」「実装した」「テスト成功」といった自己申告だけで、確認結果をPASSとしてはいけません。可能な範囲で次の証拠を示します。

- ソース変更：実際の変更ファイル、差分、関連するクラス・メソッド
- ビルド / テスト：実行コマンド、終了コード、テスト件数、成功・失敗・スキップ数
- DB：接続先、対象スキーマ、検証したデータ・制約・実行前後の状態
- トランザクション：例外発生後に対象データが残っていないことなど、要件に対応した確認結果
- 並行処理：独立したトランザクションや競合条件を実際に検証した証拠
- UI / API：実際に操作・呼び出しした範囲、入力、応答、表示結果

証拠を取得できない場合は、その理由を記載し、`NOT RUN`、`BLOCKED`、`未確認`など適切な区分を使用します。テストコードが存在することと、そのテストが実行され期待動作を検証したことを混同してはいけません。

------------------------------------------------------------------------

# 37. 変更影響範囲と回帰確認

## 【AI FIXED RULE】

変更前に、変更予定ファイルと変更しないファイルを区別します。変更中に予定外のファイルを変更する必要が生じた場合は、その理由と影響を明確にします。

ソース、SQL、DB定義、設定、API、画面などを変更した場合は、変更箇所から呼び出し元・呼び出し先・利用データ・画面・API・関連テストへの影響を追跡します。

修正前に、影響範囲と再実行すべきテストを決めます。修正後は、変更箇所のテストに加え、影響範囲に応じた回帰テストを実行します。影響しないと判断した場合は、その根拠を記載します。

------------------------------------------------------------------------

# 38. テストレベルと完了判定の区別

## 【AI FIXED RULE】

テストは、目的に応じて次の3段階に分けて報告します。

1. **変更箇所のテスト**：変更した処理を検証する
2. **関連回帰テスト**：影響を受ける周辺機能を検証する
3. **全体テスト**：既存機能を含む全体への影響を確認する

一部のテストが成功しても、未実施のテストまで成功したものとして扱ってはいけません。全体テストを実行していない場合は、全体テスト未実施と明記します。

テストの実施状況は、`PASS`、`FAIL`、`NOT RUN`、`NOT APPLICABLE`、`BLOCKED`で区別し、各区分の根拠を記載します。

------------------------------------------------------------------------

# 39. 工程間の引き継ぎと重複作業の抑制

## 【AI FIXED RULE】

調査・計画、実装、テスト、最終レビューの各工程では、前工程で確定した事実・判断・変更範囲・テスト計画を引き継ぎます。

後工程で同じ調査やテストを理由なく繰り返してはいけません。ただし、ソースの差異、追加修正、証拠不足、実行環境の変化など、再確認が必要な根拠がある場合は必要な範囲で再確認します。

引き継ぎ内容と実際のファイルに差異があれば、その差異を記録してから作業を進めます。引き継ぎ文だけを信頼し、現在の成果物を確認せずに作業してはいけません。

------------------------------------------------------------------------

# 40. 作業終了ゲートと変更凍結

## 【AI FIXED RULE】

次の条件を満たしたら、今回の作業を終了します。

- 要件・設計・実装・DB / SQL・テストの整合性を確認した
- 今回の変更差分を確認した
- 必要なテストを実行し、実際の結果を記録した
- 未実施・未確認事項と残存リスクを明記した
- 重大な未解決事項がない、または人間の判断事項として分離した
- 作業前から存在した変更・未追跡ファイルを保護した

終了条件を満たした後は、好みや見栄えだけを理由に変更を追加しません。新たな問題を発見した場合は、今回の完了に必須の問題か、別途対応できる改善かを分類します。

Gitの`add`、`commit`、`push`は、ユーザーから明示的に依頼されない限り実行しません。


# 41. 人が読みやすい出力・報告ルール

## 【AI FIXED RULE】

### 41.1 基本方針
- 作業結果は、利用者が短時間で全体像・問題・判断事項を把握できる構成で報告します。
- 原則として「結論 → 要約 → 詳細 → 根拠・証拠 → 未解決事項 → 次の対応」の順に記載します。
- 最初に結論と作業状態を示し、長い前置きや作業過程の逐次説明は避けます。
- 要約を記載しても、判断・検証に必要な詳細や根拠を省略してはいけません。
- 既存のプロンプトで指定された報告項目は維持し、項目を削除するのではなく読みやすく整理します。

### 41.2 作業状態の表記
- 作業全体の状態は、次のいずれかで明記します。
  - **完了**：依頼された作業と定義済みの完了条件を満たした。
  - **一部完了**：一部は完了したが、未実施・未解決の項目がある。
  - **未完了**：完了条件を満たしていない、または作業を開始・継続できない。
- 個別確認の状態は `PASS`（確認成功）、`FAIL`（確認失敗）、`未実施`、`BLOCKED`（環境・権限・依存条件などにより実施不能）を区別します。
- 未実施やBLOCKEDをPASSとして扱わず、全体状態と個別テスト結果を混同しません。

### 41.3 表・箇条書きの使い分け
- 複数ファイルの変更、要件との対応、テスト結果、問題一覧、未解決事項は原則として表で示します。
- 手順や確認項目は番号付きリストまたはチェックリストを使用します。
- 一つのセル・箇条書きに複数の論点を詰め込まず、必要に応じて分割します。
- 表が横に長くなりすぎる場合は、表を分割するか、詳細を項目別に記載します。
- 重要度は `高・中・低` など定義した基準で示し、色や記号だけに依存しません。

### 41.4 変更・問題の説明
- ファイル変更は、少なくとも「ファイル／変更内容／理由・要件との対応／確認方法」を示します。
- 問題は、少なくとも「問題／発生条件・根拠／影響／対応／対応後の確認結果」を示します。
- コード位置を示せる場合は、ファイルパスとクラス・メソッド・行番号などを示します。行番号が変動し得る場合は、クラス・メソッド名も併記します。
- 重要な判断には根拠を添え、事実・推測・提案を区別します。

### 41.5 テスト・証拠の表示
- テスト結果は、対象・実行コマンド・結果・実行件数・失敗件数・証拠を可能な範囲で示します。
- 実行していないテストは「未実施」と明記し、実行したかのような表現をしません。
- ログやコマンド出力は必要な箇所を抜粋し、長いログ全文は必要な場合を除いて本文に貼り付けません。保存場所が確認できる場合はそのパスを示します。
- PASS判定には、テスト出力・差分・検索結果など、実際に確認した根拠を対応付けます。

### 41.6 未解決事項と人の判断
- 未解決事項は「内容／未解決の理由／影響／人に必要な判断・作業／判断期限または次のタイミング」を示します。
- 人の判断が不要な調査や修正を、漠然とユーザーへの質問に置き換えません。AIが調査できることは先に調査します。
- 未解決事項がない場合は「なし」と明記します。
- 最後に、利用者が次に行う必要がある作業だけを簡潔に示します。不要な次作業を作りません。

### 41.7 推奨する報告テンプレート
1. **結論・作業状態**
2. **要約（重要点3〜5件）**
3. **変更内容・問題一覧**
4. **確認・テスト結果と根拠**
5. **未実施・未解決・残存リスク**
6. **人の判断が必要な事項／次の対応**

工程別プロンプトの報告形式がこの構成より詳細な場合は、工程別の項目を優先して維持し、このルールの順序・表形式・状態表記を適用します。
