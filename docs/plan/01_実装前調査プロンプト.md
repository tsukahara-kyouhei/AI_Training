# 01_実装前調査プロンプト

## 目的
実装開始前に要件・設計・既存実装・DB / SQL・テストを横断確認し、変更範囲、期待結果、未解決事項を確定する。原則として、この工程ではコードを変更しない。

## コピペ用プロンプト

```text
次のルールと工程指示に従って作業してください。

【共通ルール】
- AI_CODING_RULES.md（実際のファイル名に合わせる）

【今回の対象】
- 機能ID：[対象機能のIDを記載。未採番の場合は「なし」]
- 機能名：[対象の機能名を記載]
- 依頼内容：[今回調査してほしい内容を記載]
- 要件・設計書：[対象となる要件定義書・設計書のファイルパスを記載。なければ「なし」]
- 関連ソース / SQL / DB定義：[関連するソース・SQL・DB定義のファイルパスを記載。なければ「なし」]
- 関連テスト：[関連するテストコード・テスト資料のファイルパスを記載。なければ「なし」]
- 補足・確定済み判断：[補足事項や確定済みの判断を記載。なければ「なし」]

【禁止事項】
この工程ではソースコード、SQL、DB定義、設定、テストコードを変更しない。調査・読み取り・計画・報告のみ行う。

【調査手順】
1. 共通ルールと既存のプロジェクト規約を確認する。
2. 依頼内容から、目的、入力、処理、出力、エラー時動作、制約、対象外範囲を抽出する。
3. 要件・設計書と、関連するController / Service / Repository / Mapper / Entity / DTO / Model / Exception / Config / 画面を実ファイルで確認する。
4. DB定義、制約、インデックス、SQL、Mapper、データ型、NULL許容、初期値を確認する。
5. 既存テスト、テストデータ、実行方法を確認する。
6. 現行動作と要求仕様との差分を、根拠となる具体的なファイル・クラス・メソッド・SQL・テスト名とともに整理する。
7. 要件→設計→画面/API/DB→実装→テストの横断整合性マトリクスを作成する。
8. 変更対象ファイルと変更しないファイルを分け、API・DB・共通処理・既存機能への影響を整理する。
9. 正常系、異常系、境界値、NULL / 空文字 / 空白、不正値、DB / SQL、API / 画面、回帰、トランザクション・並行実行（該当する場合）のテスト計画を作る。
10. 各テストの入力・前提条件・期待結果・根拠資料を実装前に定義する。
11. 未解決事項を「AIが調査して解決」「人間の判断が必要」「今回の実装に影響しない」に分類する。
12. 仕様が確定していない事項が実装結果を左右するか判定する。

【判断ルール】
- 確認済み事実、要件、承認済み設計判断、推奨、未確認を明確に区別する。
- 名前・パラメータ・レスポンス・カラム・エラーコード等を推測しない。
- 既存実装と要件・設計が異なる場合、現行実装をそのまま最終仕様とみなさず、差分と根拠を報告する。
- ソースや設計書を調べれば解決できる事項は、質問前に調査する。
- API / DB / ビジネスルール / セキュリティ / トランザクション / ユーザーに見える動作の判断が必要なら、選択肢と影響をまとめて質問し、勝手に決めない。
- 無関係なファイル・機能に変更範囲を広げない。
- DB / API / ライブラリ / 設定の変更が必要と考えられる場合は、必要性と影響を報告し、この工程では実施しない。

【報告形式】

## 1. 要件・設計の要点
- 目的：
- 入力・前提条件：
- 期待する処理・出力：
- エラー時の動作：
- 対象範囲 / 対象外範囲：
- 根拠資料：

## 2. 現行実装の確認結果
| 領域 | 確認したファイル・箇所 | 現在の動作 | 根拠・注意点 |
|---|---|---|---|

## 3. 成果物横断の整合性マトリクス
| 要件・設計項目 | 要件 | 設計 | 画面/API/DB | 実装・SQL | テスト | 判定 | 根拠・対応 |
|---|---|---|---|---|---|---|---|

判定は「一致 / 不一致 / 未確認 / 対象外」。不一致・未確認は具体的な箇所と対応方針を示す。

## 4. 要件・設計との差分
| # | 項目 | 現行実装 | 期待仕様 | 根拠 | 対応方針 |
|---|---|---|---|---|---|

## 5. 変更対象案と影響範囲
| ファイル | 変更内容 | 理由 | 影響先 | 変更しない関連ファイルと理由 |
|---|---|---|---|---|

- DB / SQL：
- API / 画面：
- 共通処理・既存機能：
- セキュリティ・認証認可：
- トランザクション：

## 6. テスト計画
| テストID | 区分（変更箇所/関連回帰/全体） | 観点 | 前提・入力 | 期待結果 | 根拠 | 優先度 |
|---|---|---|---|---|---|---|

該当しない観点は理由を記載する。全体テストが必要か、今回実行可能かも明記する。

## 7. 未解決事項
| # | 分類（AI調査/人間判断/影響なし） | 内容 | 根拠 | 影響 | 選択肢・推奨案 | 実装前に解決必須か |
|---|---|---|---|---|---|---|

## 8. 実装開始ゲート
各項目を「確定 / 未確定 / 対象外」で判定する。
- 期待仕様と根拠
- 横断整合性
- 変更対象と影響範囲
- API / DB / SQLへの影響
- テストケースと期待結果
- 回帰テスト対象
- 未解決事項

最終判定：
- 実装開始可：実装に影響する未解決事項がない
- 条件付きで開始可：未解決事項はあるが、実装結果に影響しない理由が明確
- 実装開始不可：仕様判断や根拠確認が必要

## 10. 共通の出力ルール
出力の見やすさ、作業状態の表記、根拠の示し方、テスト結果の表記は、`AI_CODING_RULES.md` 第41章「人が読みやすい出力・報告ルール」に従ってください。このプロンプト内の工程固有の報告項目は省略せず、共通ルールと矛盾しない形で維持してください。

実際に確認していない内容を確認済みと報告しないでください。コード変更は行わないでください。
```
