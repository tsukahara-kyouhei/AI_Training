## 1. 機能概要

- Controllerで処理されなかった例外を共通の形式で記録し、システム運用者が発生箇所や原因を調査できるようにする。
- クライアント起因のエラーとシステムエラーを区別してログに記録し、障害状況の把握を支援する。
- 例外を記録した後も元の例外処理へ引き継ぎ、エラー応答など既存の処理を継続できるようにする。

## 2. 入出力項目

| 項目区分 (入力/出力) | 項目名 | 説明 |
|---|---|---|
| 入力 | HTTP リクエスト URI | 例外が発生したリクエストのパス。ログの `path` として記録する。 |
| 入力 | Controller の未処理例外 | Controller 内で処理されなかった `Exception`。 |
| 入力 | 例外の HTTP ステータス・理由 | `ResponseStatusException` が 4xx の場合に、ステータスと理由を警告ログへ記録する。 |
| 入力 | 例外メッセージ・スタックトレース | 4xx 以外の例外について、メッセージと例外情報をエラーログへ記録する。 |
| 出力 | 警告ログ | 4xx の `ResponseStatusException` を `event`、`path`、`status`、`message` とともに記録する。 |
| 出力 | エラーログ | その他の例外を `event`、`path`、`message`、例外情報とともに記録する。 |
| 出力 | 例外の再送出 | 記録した例外をそのまま再送出し、後続の共通エラー処理へ引き継ぐ。 |

## 3. 処理フロー

### `logUnhandledException`

1. Controller で未処理となった例外を受け取り、リクエスト URI を取得する。
2. 例外が 4xx の `ResponseStatusException` の場合：
   1. イベント、リクエスト URI、HTTP ステータス、理由を警告ログに記録する。
   2. 元の例外を再送出する。
3. それ以外の例外の場合：
   1. イベント、リクエスト URI、例外メッセージ、例外情報をエラーログに記録する。
   2. 元の例外を再送出する。
